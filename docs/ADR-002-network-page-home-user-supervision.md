# ADR-002: Network Page Redesign for Home-User Router Supervision

> **2026-07-26 note:** Home mode was removed wholesale by WARP-1341 (commit
> `34d4ce6d` — the workspace is business-only). This ADR's home-persona scope
> is therefore historical; the network-page supervision principles survive,
> but the "everyday home user" persona framing no longer applies.

**Status:** Proposed
**Date:** 2026-04-16
**Deciders:** Engineering team
**Source:** Dashboard persona audit (2026-04-16), OpenWrt integration audit (2026-04-16), ADR-001, `docs/ROADMAP.md` M2.5

## Context

The `/network` page in the web dashboard is the user's primary surface for router supervision: WiFi, devices, firewall, guest access, system health. Three things drive this ADR:

1. **The backend is mature, the UI is persona-mismatched.** The orchestrator exposes ~30 network routes (`apps/orchestrator/src/routes/network.ts`), the routing service wraps ubus/uci with safe-apply + rollback (`services/routing/main.py`), and the OpenWrt overlay grants a scoped `droplet-ai` ACL (`openwrt/files/usr/share/rpcd/acl.d/droplet-ai.json`). The dashboard is wired to all of it, but surfaces installer-grade concepts (zones, VLANs, rules) to end users. Target persona is the **everyday home user**, not a network admin.

2. **The OpenWrt integration has real seams.** A focused audit found unauthenticated calls between orchestrator and routing service, plain-env credentials, no retry/backoff, and silent empty-default masking on failures. Building new features on top of this foundation will turn small OpenWrt hiccups into support tickets. See "Phase 0.5 — Integration hardening" below.

3. **Related work in flight.** PR #5 (Lantronix switch driver + camera-subnet provisioning) adds orchestrator routes and touches `schema.prisma`. It should land first to avoid migration conflicts.

## Decision

Redesign `/network` around a home-user information architecture with **progressive disclosure**: simple controls on top, installer controls preserved under an **Advanced** toggle. Before building new features, harden the OpenWrt integration so failures are safe, typed, and observable.

**Persona:** Home user.
**Auth:** Existing Nextcloud SSO is sufficient; no new RBAC work.
**OpenWrt strategy:** Vanilla OpenWrt + overlay (unchanged).
**Priority order:** Config first, then observability.
**Feature order:** Device intelligence → Alerting → Guest network lifecycle.

## Information architecture

Three-tier progressive disclosure, persisted per user in `localStorage` under `droplet.network.showAdvanced`:

| Tier | Content | Default |
|---|---|---|
| Primary | Devices (named + grouped), WiFi (SSID / password / QR), Guest network, Alerts feed | Visible |
| Secondary | WAN status, interface health, firmware state | Collapsed cards |
| Advanced | Firewall zones / rules, VLANs, port forwards, static DHCP, camera subnet, reboot | Hidden behind toggle |

## Options considered

### Option A — Redesign `/network` around home-user IA (chosen)

| Dimension | Assessment |
|---|---|
| Complexity | Medium |
| Cost | 3–4 sprints phased |
| Team familiarity | High (stack unchanged) |

**Pros:** Clean persona fit, reusable pattern for `/storage` and `/cameras`, forces us to fix the integration gaps.
**Cons:** Discards some React table code; first PR is the largest.

### Option B — Keep current tabs, add a "Simplify" mode toggle

**Pros:** Low risk, fast.
**Cons:** Two UIs to maintain; default view still shows zones and rules — fails the persona.

### Option C — Split into `/home` + `/network/advanced` pages

**Pros:** Clear separation.
**Cons:** Two entry points confuse end users; navigation clutter.

## Trade-offs

- Persona clarity beats code reuse — the current UI treats every visitor as an installer. A toggle layered on top compounds the problem instead of solving it.
- `NetworkDevice` and `NetworkEvent` tables are cross-cutting; cameras and storage will want to write `NetworkEvent` too. The event enum must be designed extensibly from day one.
- Offline-first: no external OUI API, no cloud alert routing, no QR generation via third-party service. Everything ships on the device.
- Phase 0.5 (integration hardening) and PR #5 both touch `schema.prisma` — serialize by merging PR #5 first.

## Plan

### Phase 0 — Housekeeping

1. Review and merge PR #5 (Lantronix switch + camera subnet).
2. Inventory current `/network` components against the new IA — keep, refactor, or demote to Advanced.

### Phase 0.5 — Integration hardening

Ships before any new features are built on the router surface.

1. **Shared-secret bearer between orchestrator and routing service.** New env `ROUTING_SERVICE_TOKEN` generated by `setup.sh` alongside `DEVICE_SECRET`. Routing service rejects unauthenticated calls via FastAPI dependency. Orchestrator injects the header in `openwrt.client.ts` on every call. No mTLS — overkill for same-host Docker; revisit if we split hosts.

2. **`OPENWRT_PASSWORD` out of env, into a file-mounted Docker secret.** `/run/secrets/openwrt_password` with `0600` permissions. Routing service reads on startup. `setup.sh` generates and writes the file. Never in Compose env.

3. **Retry wrapper around `openwrt.client.ts`.** Single `fetchRouting<T>()` helper — 3 attempts, 100 / 250 / 1000 ms backoff with jitter, abort on 4xx, retry on 5xx and network error. Replace all 20+ bare fetches.

4. **Typed errors instead of silent empty defaults.** `getNetworkOverview()` returns `Result<NetworkOverview, RouterError>` where `RouterError.code ∈ { UNREACHABLE, TIMEOUT, AUTH, ROLLED_BACK }`. Dashboard renders a targeted error state per code (reconnecting / check router / auth fix / rolled back).

5. **Wire safe-apply rollback to the UI.** Routing service emits `Operation-Id` header on every write. Orchestrator exposes `GET /network/operations/:id` returning `applied | rolled_back | pending`. After a Tier 2 confirm, the dashboard polls the operation until terminal and shows "Rolled back — connectivity check failed" when applicable.

6. **Align confirmation-token TTL to safe-apply timeout.** Both 60s. Bind the token to `{ service, action, resourceId }` so it cannot be replayed against a different operation. Update `safety-tier.service.ts` and the routing service `apply` timeout in lockstep.

7. **Type the firewall payload.** Replace `Record<string, unknown>` in `apps/orchestrator/src/types/network.ts` with `FirewallZone`, `FirewallRule`, `FirewallRedirect` schemas derived from the routing service Pydantic models (generate with `datamodel-code-generator` or hand-mirror and cover with a contract test).

8. **Rolled-up health endpoint.** `GET /orchestrator/health` aggregates routing, ai-gateway, nextcloud, postgres into `{ status: 'ok' | 'degraded' | 'down', components: [...] }`. Dashboard Overview card reads this. Docker healthcheck uses it.

9. **Make routing a default dependency.** Remove `profiles: ["full"]` from routing in `docker/docker-compose.yml`. Keep `full` for Frigate and camera-discovery. Dev laptops without a router set `OPENWRT_HOST` to a mock or skip via env flag.

### Phase 1 — Device intelligence (config-first)

1. **Prisma model `NetworkDevice`:** `mac` (PK), `displayName`, `icon`, `group`, `notes`, `vendor`, `firstSeen`, `lastSeen`, `lastIp`, `isBlocked`.
2. **Reconciler:** on each device poll, upsert observed DHCP and ARP entries into `NetworkDevice`.
3. **MAC-OUI vendor lookup:** ship IEEE registry CSV in-image (device is offline-first, no network call).
4. **Endpoints:** `GET /network/devices/:mac`, `PATCH /network/devices/:mac`.
5. **UI:** rich device card — editable name, icon picker, group chip, last-seen sparkline (30-day rolling), one-click block. Advanced exposes MAC, IP, static-lease, firewall rule reference.

### Phase 2 — Alerting

1. **Prisma model `NetworkEvent`:** `type`, `severity`, `subjectMac`, `subjectInterface`, `message`, `createdAt`, `acknowledgedAt`.
2. **Producers:**
   - New device joined (unknown MAC) — from reconciler.
   - WAN flap — poll `network.interface.wan` status, emit on transition.
   - Firmware / opkg update available — weekly check via routing service.
   - Guest SSID enabled / disabled / expired.
   - Failed router login (hostapd / uhttpd logs).
3. **Channels:** in-app bell and `/network` Overview feed now; push and email deferred.
4. **Debounce:** known-device re-join is not an alert; only first-seen MACs page the bell.

### Phase 3 — Guest network lifecycle

1. Extend `POST /wifi/guest` in routing service to accept `{ expiresAt, bandwidthLimit? }`.
2. BullMQ job on Redis disables guest SSID at expiry.
3. **UI:** single card — toggle, QR code (`qrcode` npm lib, offline), expiry picker (1h / 1d / 1w / custom / never), regenerate-password button.
4. Leverage PR #5 VLAN work to keep guest traffic isolated on its own subnet.

### Phase 4 — Advanced panel parity

- Move existing Firewall / VLAN / PortForward tables under an `<AdvancedPanel>` component.
- `localStorage` key `droplet.network.showAdvanced` drives visibility.
- Consistent Tier-2 confirmation modal for all write actions.

## Consequences

**Easier:** Home users can rename "Samsung-AD3F" → "Kitchen TV", block a kid's phone, and hand out a 1-hour QR-coded guest WiFi without touching a zone. Device intelligence unlocks future QoS, parental controls, and schedules without more backend work. Integration hardening makes OpenWrt hiccups visible and recoverable instead of silent.

**Harder:** We need a reusable progressive-disclosure component. `NetworkEvent` becomes a cross-subsystem contract to own carefully. Phase 0.5 pushes feature work by ~2 sprints.

**Revisit:** When WireGuard remote access lands (M2.6), remote-access UI slots under Advanced. When the general audit log (PH3 gap in ADR-001) lands, it reuses `NetworkEvent` table or a sibling.
