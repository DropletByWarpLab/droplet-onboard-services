# ADR-022 — Matter controller as a host-network sidecar (WARP-850)

**Status:** accepted  
**Date:** 2026-06-10  
**Ticket:** [WARP-850](https://warp-lab.atlassian.net/browse/WARP-850)

## Context

The Matter controller (`matter.js` `CommissioningController`) was embedded in
the orchestrator process. The orchestrator container runs on the compose
**bridge** network, which means the controller never had:

- **BLE.** Matter devices that require Bluetooth LE for first-time
  commissioning (the majority of retail Matter-over-Wi-Fi devices) could never
  be paired. matter.js logged "BLE is not enabled on this platform" at every
  start, and WARP-851 had to ship an honest "BLE commissioning isn't available
  on this box" notice in the dashboard.
- **LAN mDNS.** Commissionable-device discovery (`_matterc._udp`) and
  operational discovery (`_matter._tcp`) ride link-local multicast. The bridge
  network is its own broadcast domain: the controller saw neither the home LAN
  nor the Droplet's own Wi-Fi clients. Commissioning of devices already on IP
  failed with `CommissionableDeviceDiscoveryFailedError` ("No device discovered
  using identifier …"), the exact failure WARP-851 mapped to honest copy.

Host facts verified live on the single-box (2026-06-10): Intel AX210
(Bluetooth 5.3) at `hci0`, bluez installed, `bluetooth.service` active,
`btmgmt info` shows `le` in current settings, kernel 6.17. The in-container
OpenWrt AP's `br-lan` is a **host** bridge, so the host's init network
namespace can multicast to the Droplet's own Wi-Fi clients natively.

## Options considered

1. **Extract the controller into a host-network sidecar service** (chosen).
   A new `services/matter-controller` owns matter.js and runs with
   `network_mode: host` + `cap_add: [NET_ADMIN, NET_RAW]`. It gets raw HCI
   sockets (BLE) and native multicast on every host interface (home LAN +
   br-lan). The orchestrator becomes an HTTP client over the established
   host-service pattern (routing 8080, switch 8081, display 8082 →
   matter-controller 8083 via `host.docker.internal`).

2. **Move the whole orchestrator container to `network_mode: host`.**
   One-line compose change, no extraction. Rejected: the orchestrator is the
   box's main API surface and sits at the center of the compose service mesh
   (db, cache, broker, nextcloud, ai-gateway by service name — all of which
   break on host network); it would expose :3000 directly on the host,
   collide with the host-port ladder, widen the blast radius of any
   orchestrator compromise to the init netns, and hand raw-socket
   capabilities to a process that runs LLM-driven tool dispatch.

3. **Bridge the gap into the existing container: mDNS reflector + BLE
   passthrough.** Run avahi-daemon with `enable-reflector` (or a dedicated
   mDNS repeater) between the bridge network and the LAN, and pass Bluetooth
   through to the container (D-Bus socket mount or `/dev` passthrough).
   Rejected: reflection of Matter's mDNS is fragile (TTL/interface handling,
   unicast-response quirks, doubled answers) and adds a daemon whose failure
   mode is silent discovery loss; and matter.js's BLE layer
   (`@matter/nodejs-ble` → `@stoprocent/noble`) speaks raw HCI sockets, not
   BlueZ D-Bus — so a D-Bus passthrough doesn't help, and raw HCI inside a
   bridge-network container needs the host netns anyway (HCI sockets are
   network-namespace scoped). This option re-derives option 1 with extra
   moving parts.

## Decision

Option 1. The controller moves to `services/matter-controller` (Node +
TypeScript + matter.js), and the orchestrator's `matter.service.ts` keeps its
module path and export surface but becomes an HTTP client of the sidecar.

Key properties:

- **Single consumer + auth.** Only the orchestrator talks to the sidecar.
  Auth is a shared token in the `X-Droplet-Auth` header (device-bridge
  precedent), `DROPLET_MATTER_SERVICE_TOKEN`, generated by `setup.sh` into
  `.env`; the sidecar fails closed when it's empty.
- **Fabric continuity.** The `matter-data` named volume moves to the sidecar
  unchanged, the matter.js environment id stays `droplet-controller`, and
  `MATTER_STORAGE_PATH` (the one allow-listed `MATTER_*` env var — it folds to
  matter.js's `storage.path`) moves with it. Commissioned fabrics survive the
  migration without re-pairing.
- **BLE at process start.** `@matter/nodejs-ble` is registered into
  `Environment.default` when the sidecar process starts — never inside init —
  so the `bleCommissioning` capability answer is decided once per process and
  never flips mid-boot. The native HCI module is a dynamic import with
  graceful degrade to IP-only (no adapter / module unavailable / native stack
  fails to load), so Windows dev installs and CI build and test cleanly.
- **Error contract preserved.** The sidecar passes raw matter.js error class
  names + messages through its HTTP responses (`errorClass`, `errorMessage`);
  the orchestrator's `translateCommissionError()` (WARP-851) keeps owning the
  customer-facing copy, unchanged.
- **Events.** The sidecar fans out `state_changed` / `connection_changed`
  over SSE; the orchestrator bridges them into its existing EventEmitter so
  the dashboard-facing `/api/matter/devices/events` stream is unchanged.
- **Host prep is setup.sh-owned.** `scripts/lib/bluetooth.sh` converges the
  host to: bluez + rfkill installed, `bluetooth.service` enabled AND running,
  radio rfkill-unblocked, adapter powered. bluetoothd **stays running**:
  noble's central role uses raw-channel HCI sockets that coexist with
  bluetoothd (the exclusivity constraint applies to HCI user-channel
  consumers and to peripheral/advertising roles, which the Droplet never
  uses — it is a commissioner only), while bluetoothd is what keeps the
  adapter powered across reboots and rfkill events.

## Consequences

- The orchestrator image no longer needs HCI or multicast; its `@matter/*`
  dependencies remain only as test fixtures for the error-translation suite.
- `GET /api/matter/capabilities` now proxies the sidecar's real state:
  `bleCommissioning: true` on the shipping box once the AX210 registers.
- The sidecar is restart-independent: the orchestrator's client reconnects
  (SSE bridge with backoff) and `isMatterInitialized()` self-heals, so a
  sidecar upgrade does not require an orchestrator restart.
- One more always-on host-network container (~256 MB ceiling per the ADR-021
  pattern: `DROPLET_MATTER_MEM_LIMIT`, default 256m — DROPLET-prefixed, not `MATTER_CONTROLLER_*`, so the operator-facing .env knob can never enter matter.js's `MATTER_*` auto-import scope).

## Risks

- **BLE/Wi-Fi antenna coexistence on the AX210.** The AX210 shares antennas
  between Wi-Fi and Bluetooth. On the single-box the same host also runs the
  OpenWrt AP — heavy AP traffic during a BLE commissioning window can degrade
  BLE throughput/latency (and vice versa). Intel's firmware coexistence
  generally handles this, but commissioning retries may be needed under load;
  if support sees flaky BLE pairing on busy networks, this is the first
  suspect. Mitigation if it materializes: a USB BT dongle on a separate
  radio (`DROPLET_MATTER_BLE_HCI_ID` selects the adapter).
- **bluetoothd interference.** Kept-running bluetoothd is the documented-good
  configuration for noble's central role, but a future BlueZ behavior change
  (e.g. aggressive autonomous LE scanning) could contend with raw-channel
  scans. The coexistence decision and its rationale live in
  `scripts/lib/bluetooth.sh` so there is exactly one place to revisit.

## Non-goals

- **Thread.** The box has no 802.15.4 radio and this ADR adds none — the
  sidecar is NOT a Thread border router. Matter-over-Thread devices can only
  join through a third-party border router already on the LAN (in which case
  they commission like any IP-reachable Matter node). BLE commissioning here
  covers Matter-over-Wi-Fi onboarding.
- Multi-fabric admin features, bridging, or exposing the sidecar to any
  consumer other than the orchestrator.
