## Context

A Droplet serves its dashboard (and Plane on `:8443`, Nextcloud under `/nextcloud/`) over HTTPS from the in-box nginx `gateway`, which reads a **self-signed** certificate generated by `scripts/lib/secrets.sh::_generate_tls_cert` (CN "Droplet Edge Device", RSA-2048, 10-year, SAN = friendly hostnames + LAN IPs). Because the cert is self-signed, every client device hits a browser "Not secure" interstitial unless it first runs `scripts/trust-droplet-cert.{sh,ps1}` to inject the cert into its OS trust store — a per-client install. `setup.sh` (≈L535-540) instructs the operator to do this on every phone, laptop, and tablet. The launch-readiness audit filed this as [WARP-584](https://warp-lab.atlassian.net/browse/WARP-584) ("document the trust-flow UX + roadmap an internal-CA/ACME option").

This is unacceptable for customers: there is no path to a green padlock without each device clicking through a warning or running an installer.

**ADR-009 currently forbids the obvious fix.** It states (L119-123): "*Off-LAN … the same `https://droplet.local` URL resolves through the tunnel to the Droplet's LAN IP. **No public TLS endpoint** on the orchestrator — the only inbound is via WG*", and (L212-214) "***Do not add a public TLS endpoint to the orchestrator.** Off-LAN access goes through WireGuard, full stop.*"

That ruling has two intertwined motivations that this ADR **separates**:

1. **No public *reachability*** — the box's home IP must never be exposed to the public Internet; there must be no inbound attack surface on a customer LAN. **This ADR fully preserves that.**
2. **An implicit consequence** — "therefore the cert is self-signed and trust is a local problem." **This ADR amends only this part.**

Crucially, ADR-009 already *aspires* to "the same DNS name resolves on-LAN and off-LAN through the tunnel." In the field that aspiration is unmet: `.local` names do not cross a WireGuard tunnel, so the only address that works off-LAN today is the bare `https://192.168.20.1` (see PR #582). This ADR realizes ADR-009's own intent — one DNS name, everywhere — and gives it a publicly-trusted certificate.

`warp-lab.ai` is confirmed authoritative on **Cloudflare** nameservers, so ACME **DNS-01** can be automated directly on that zone. A box cannot safely hold a DNS-write credential (it would sit on customer hardware), so issuance is **HQ-mediated**: the box generates its own keypair + CSR and the HQ performs the DNS-01 dance with that CSR. This becomes the first concrete capability of the fleet HQ (`hq.warp-lab.com`) specced in FLEET_MANAGEMENT_DESIGN.md, and answers ADR-016's open question #2 ("does Warp provide a per-box subdomain + ACME?").

## Decision

1. **Publicly-trusted certificate per device**, from Let's Encrypt via **HQ-mediated Cloudflare DNS-01**. The box generates its own TLS keypair + CSR; **the private serving key never leaves the box**. HQ runs the DNS-01 challenge on `warp-lab.ai` and returns the signed leaf + chain only.
2. **Opaque per-device subdomain** `d-<hmac>.devices.warp-lab.ai`, where `<hmac>` = truncated **HMAC-SHA256(HQ-secret, device_id)**, computed and stored HQ-side. Certificate Transparency publishes every issued name, so the label MUST carry **no customer PII**; a *keyed* HMAC (not a bare hash) prevents a CT-log enumerator from confirming a guessed `device_id`.
3. **Split-horizon resolution, NO public A/AAAA record.** The box's own dnsmasq answers the FQDN with the **LAN IP** for at-home clients and with **192.168.20.1** (the WireGuard gateway) for tunnel clients. Only a *transient* `_acme-challenge` TXT record is ever created in public DNS (and deleted after each order). From the public Internet the FQDN has **no A/AAAA record** (NXDOMAIN in steady state; NODATA during the brief DNS-01 challenge window when the `_acme-challenge` TXT makes the label an empty non-terminal) — the box is unreachable and its home IP is never published.
4. **The friendly `.local` name stays a LAN-only convenience.** mDNS `droplet-ai.local` keeps working at home, uncertified-publicly (it cannot cross the tunnel and must not appear in CT). The single trusted-everywhere URL is the opaque FQDN; `.local` is the at-home shortcut.
5. **Bootstrap self-signed retained.** `_generate_tls_cert` still runs at setup so the box serves TLS instantly and works offline / pre-issuance / if HQ is unreachable. The per-device FQDN is added to the bootstrap cert's SAN. The LE cert overwrites the *same* `docker/certs/droplet.crt`/`.key` files (LE fullchain into `droplet.crt`) so nginx needs zero config change; the box degrades back to self-signed if the LE cert is missing/expired and HQ cannot be reached.
6. **Secrets stay HQ-only.** The Cloudflare API token (`Zone:DNS:Edit`, scoped to `warp-lab.ai`) and the fleet offline CA never ship to a box. A box holds only its own serving key + the returned chain.
7. **Issuance authentication = the WARP-230 TPM identity.** The box proves possession of its non-extractable TPM key over a single-use HQ nonce (the `DeviceIdentityService.Sign` challenge), cross-checked against the device registry row that owns the bound label. Reached over **plain outbound HTTPS to `hq.warp-lab.com`** — it does not require the fleet WireGuard tunnel, decoupling first-issuance from the rest of the fleet build. (Fleet offline-CA mTLS can be layered on as a transport second factor later.)
8. **This ADR does NOT add a public inbound TLS endpoint.** No port is opened to the Internet; off-LAN access remains WireGuard-only. ADR-009's hard rule is honored; only its self-signed-cert consequence is superseded.

## Consequences

**Easier**
- Green padlock on every client, at home and over VPN, with **no per-client install** — closes WARP-584.
- Plane (`:8443`) and Nextcloud inherit the cert automatically — the single nginx `gateway` serves all three from one cert pair.
- Reuses WARP-230 (identity) and the fleet HQ groundwork; answers ADR-016 OQ#2 and unblocks its lighter "Option A" SSO variant (external IdPs can finally redirect to a trusted public HTTPS name).
- Realizes ADR-009's own "same DNS name on-LAN and off-LAN" aspiration, which `.local` never delivered over the tunnel.

**Harder**
- Adds an HQ dependency to a previously fully-local issuance story (mitigated by the retained self-signed bootstrap + 90-day cert life + graceful degradation).
- Renewal automation must run reliably on every box (LE certs are 90 days).
- Split-horizon dnsmasq must serve the FQDN on both the LAN and wg0 views without regressing the wg0→gateway DNAT from PR #575.

**Risks**
- **CT-log enumeration** — every cert publishes its label to CT. Opaque keyed-HMAC labels + no A record mean an enumerator learns only "a Warp device exists," with no PII, no address, and no reachability. Accepted.
- **LE rate limits at fleet scale** — ~50 certs / registered-domain (`warp-lab.ai`) / week, 300 new-orders / 3h. Per-device names rule out a wildcard, so this is a hard ceiling. Note: delegating `devices.warp-lab.ai` to its own DNS zone does **not** help — LE rate limits are keyed on the eTLD+1 (`warp-lab.ai`) per the Mozilla Public Suffix List, not on DNS zone boundaries. Valid mitigations before fleet rollout: (a) request a LE rate-limit increase (recommended first step), (b) register a separate domain (e.g. `warp-devices.ai`), or (c) submit `devices.warp-lab.ai` to the Mozilla PSL as a public suffix (months-long eligibility process). Use the **LE staging** environment for all plumbing tests.
- **HQ compromise → Cloudflare token** — token is HQ-only and scoped to the single zone; a compromised box cannot mint records or certs for any other device.
- **Key custody** — serving the TPM key directly in the TLS hot path is explicitly avoided; the serving key is a separate box-local key, the TPM key is used only for identity/PoP.

## Security / Privacy

- **Home IP never published** — no public A/AAAA record; split-horizon only; `dig` from outside the LAN/VPN returns NXDOMAIN in steady state (NODATA during the brief DNS-01 challenge window).
- **CT-log subdomain exposure → opaque labels** — `d-<hmac>.devices.warp-lab.ai`, HMAC-keyed; no customer-identifying token, ever.
- **Revocation** — on decommission/compromise HQ revokes via ACME `revokeCert` and unbinds the label↔device row so renewals stop; box `factory-reset` drops the serving key and deregisters the split-horizon hostrecord. A revocation runbook is an action item.
- **HQ down** — the box serves its last-issued LE cert until near expiry; if it expires while HQ is unreachable, it falls back to the retained self-signed cert. **Implementation constraint:** `_generate_tls_cert` regenerates a fresh RSA keypair to the same file path when the cert is expired; a fallback that triggers this regeneration will produce a cert with a different keypair from the one clients imported via `trust-droplet-cert.sh`, causing hard TLS errors — not graceful degradation. The `tls-issuance.service.ts` implementation must therefore either (a) preserve the original bootstrap cert as a side-copy (e.g. `droplet.crt.bootstrap`) and restore that on fallback, or (b) keep `_generate_tls_cert` idempotent on its keypair. Until that is resolved, trust-store clients will need to re-trust after a fallback-regeneration event. Issuance/renewal retries with backoff.
- **Private-key custody** — serving key generated on-box, stored `0600` in `docker/certs/`, never transmitted; only the CSR leaves the box; the Cloudflare token + offline CA never leave HQ.
