# ADR-030: Signed, RBAC-gated app-catalog installer (design only — build deferred to post-GA)

- **Status:** Proposed
- **Date:** 2026-07-11
- **Authors:** Claude (Dev agent), for Stefan Cruceru
- **Related tickets:** WARP-908 (this ticket — docs-only ADR); WARP-180 / ROADMAP **M3.6** (Community marketplace — the GTM milestone this design resolves the architecture call for; the milestone itself stays dormant/not-started).
- **Related ADRs:** [ADR-020](ADR-020-appliance-image-build-and-flash-pipeline.md) (appliance image build + signed manifest/verify substrate — this design reuses it verbatim rather than inventing a second signing scheme); [ADR-004](ADR-004-rbac-per-route-guards.md) (RBAC — per-route `requireRole()` guards + the `owner | admin | family | guest | service` enum this design gates installs with); [ADR-009](ADR-009-canonical-system-architecture.md) / [THREAT_MODEL.md](THREAT_MODEL.md) T5.3 (the orchestrator is deliberately **docker-socket-free** — this design must not reopen that boundary).

## Context

A competitor in this space ships an "app catalog": curated database rows describing third-party containers, installed one-click by a control-plane service that holds the **host Docker socket** (via `dockerode`) and does `docker run`/`docker-compose up` directly against arbitrary catalog entries. WARP-180 / ROADMAP M3.6 ("Community marketplace — framework for community-contributed tool extensions and integrations") is the dormant milestone this competitor pattern would naively map onto, and it is tempting to copy the shape wholesale: it is simple, and it demos well.

Copying it **raw** would undercut Droplet's founding thesis (`CLAUDE.md` "The Foundation") and two decisions already on record in this repo:

1. **The orchestrator is intentionally docker-socket-free.** THREAT_MODEL.md T5.3 accepts orchestrator RCE as a bounded, token-only blast radius specifically *because* the orchestrator has no Docker socket. Giving it (or any LLM-reachable surface) `dockerode` access to install arbitrary third-party images would hand a compromised or socially-engineered agent session the ability to `docker run --privileged` its way to full host control — the single scariest regression this codebase actively avoids. `services/ops-console` already demonstrates the correct pattern for *when* docker-socket access is acceptable: a separate, non-customer-facing, bearer-token-gated, `profiles: ["ops"]` service, scoped to the `com.docker.compose.project=droplet` label, never reachable from chat/LLM tool-calling.
2. **Droplet already has a signed, fail-closed distribution substrate.** ADR-020 built exactly the pieces a catalog installer needs — a signed `manifest.json` (schema, ECDSA-P256 detached signature, per-asset sha256, fail-closed `verify`), a `releases` repo pattern, and a CLI (`scripts/droplet-image`) that signs/verifies/publishes. M3.4 (OTA) already plans to consume this substrate for stack updates. An app catalog is the same problem shape — "install a versioned, attested artifact onto this box" — one level down (per-extension instead of whole-image). Building a second, unsigned, ad-hoc install path (raw `docker pull` of whatever a catalog row names) would duplicate that trust work worse and skip the attestation Droplet already has for everything else on the box.

This ADR is **docs-only**: it commits to a design and an explicit deferral, and does not implement anything. WARP-908 is the ticket for this ADR; the design itself belongs to WARP-180 / M3.6, which stays `[ ]` Not started in `docs/ROADMAP.md` — this ADR does not change that status, it removes the "what would we even build" ambiguity for whenever M3.6 is picked up.

## Decision

### D1 — Curated + signed, not free-form Docker-socket installs

The catalog is a **curated list of extension manifests**, each pointing at a container image + declared capability surface, **signed by Warp Lab** (or, later, by a trusted community-signing tier) — never an arbitrary `docker run <anything>` against operator/community-submitted rows. Concretely:

- Each catalog entry is an `extension-manifest.json` (schema versioned like `scripts/image/manifest.schema.json`) naming: extension id, version, image reference (registry + digest, **not** a mutable tag), declared MCP tool surface (which `@droplet/tools-core` tool namespaces it registers, if any), required compose profile/resource footprint (reuses the ADR-021 `*_MEM_LIMIT` pattern), and required RBAC role floor to install.
- The catalog itself is a signed index (`catalog-manifest.json`), following the **exact** ADR-020 contract: detached OpenSSL ECDSA-P256 signature over the manifest, SHA-256 over every listed asset, verified fail-closed by a `droplet-catalog verify` step modeled 1:1 on `droplet-image verify` (same key-custody model — see `scripts/image/keys/README.md` — same rotation/superset-trust procedure, same explicit ban on Ed25519/minisign per `docs/security/fips-allowed-algorithms.md`). Reusing the substrate outright — not "ADR-020-inspired" — means one signing key, one verify code path, one rotation runbook to audit, instead of two.
- **Install still never touches a host Docker socket from a customer-reachable process.** The install step is a **new, narrow, orchestrator-owned endpoint** that, after `verify` passes and RBAC passes (D2), hands the pinned image digest + compose fragment to the **existing** host-side install surface the orchestrator already uses for privileged host operations without a socket mount — the device-bridge / polkit-routed root unit pattern named in ADR-020 §D6 (`50-droplet-device-bridge.rules`, `NoNewPrivileges`), the same boundary `update-agent/host-compose-runner.ts` already crosses for OTA-applied container updates. No new dockerode dependency, no new socket mount, no new privileged surface — the catalog installer is a **consumer** of the update-agent's existing "apply a verified compose change to the host" capability, not a second implementation of it.
- Community-contributed rows (the literal M3.6 "community-contributed tool extensions" scope) are **out of scope until a signing-delegation model exists** — see Consequences. Phase 1 catalog entries are Warp-Lab-authored/signed only.

### D2 — RBAC: `owner`/`admin` only, `requireRole()` guard, per-extension floor

Catalog **browse** (list available/installed extensions) is readable by any authenticated role, matching the existing MCP RBAC convention (`requiresWrite === false` reads are open to `family`/`guest`). Catalog **install/uninstall/upgrade** requires `requireRole("owner", "admin")` on the new route — the identical guard already used for every other install/administrative mutation in `apps/orchestrator/src/routes/` (e.g. `auth.ts`'s user-management routes, `aps.ts`). An individual extension manifest may additionally declare a **stricter** floor (e.g. `owner`-only for an extension that requests broad LAN device control), but can never *loosen* below `owner`/`admin` — the route guard is the hard floor, the manifest can only tighten it. If the extension registers new LLM-callable tools, those tools carry their own `requiresWrite`/`requiresConfirmation` flags through the normal `@droplet/tools-core` registry path (ADR "Adding a new tool" convention in `CLAUDE.md`) — the catalog does not introduce a second tool-registration mechanism.

### D3 — Advisory-vs-block preflight validation (the pattern worth borrowing)

The one part of the competitor's design genuinely worth adopting is its **two-tier preflight check** before an install proceeds, run against the box's live state:

- **Block (hard-fail, install refused):** signature/verify failure; RBAC floor not met; declared resource footprint exceeds free capacity under the ADR-021 memory-limit budget; image digest unreachable/unverifiable; a declared port/profile conflicts with a running default-on service.
- **Advisory (warn, but the operator may proceed):** the extension is unmaintained/older than N releases; it declares an optional capability (e.g. camera access) the box doesn't currently have hardware for; it duplicates functionality of an already-installed extension; disk headroom is tight but not exhausted.

This mirrors a pattern already precedented in this repo's philosophy of graded checks — `scripts/test/ship-check.sh` runs independent named checks where some are launch-blocking and others are advisory-only in lighter modes, and `docs/security/egress-audit.md`'s allowlist already distinguishes a **required** match (host+port) from an **advisory** hint (`destination.protocol`) that narrows without ever being the sole basis for a block. The catalog installer's preflight follows the same shape: every check is independently named and typed `block` or `advisory` up front (not inferred from its failure message), and only `block`-typed failures stop the install. The UI (future `/extensions` route named in `docs/ROADMAP.md` M3.6) surfaces both tiers distinctly — advisories are dismissible, blocks are not.

### D4 — Explicit deferral: no build before post-GA

**This ADR is a design commitment, not a build authorization.** No code, schema, route, or dashboard surface for the app catalog ships as part of WARP-908. `docs/ROADMAP.md` M3.6 remains `[ ]` Not started with its existing blockers (sandbox contract with `inference-engine`'s OpenClaw; signing/trust model — this ADR resolves the signing/trust half of that blocker but not the sandbox half). The build is explicitly deferred until **after GA**, gated on:

1. The sandbox-execution contract with `inference-engine` (OpenClaw) landing — an installed extension's *runtime* behavior (what it's allowed to do once running) is a separate, harder problem than what this ADR solves (what's allowed to be *installed* and by whom), and M3.6's own blocker list already names it.
2. GA priorities (M1–M2 milestones) clearing first — WARP-180/M3.6 sits after the OTA update system (M3.4) in the GTM sequence, and this ADR's install mechanism is built *on top of* the M3.4 update-agent path (D1), so it cannot land before that path is production-hardened.

## Consequences

- **Positive:** M3.6's "what would we even build" ambiguity is resolved without inventing new trust infrastructure — one signing key, one verify code path (ADR-020's), one RBAC convention (ADR-004's), one privileged-apply path (the existing update-agent/device-bridge boundary). The orchestrator's docker-socket-free property (THREAT_MODEL T5.3) is preserved rather than punched through for a marketplace feature.
- **Cost / caveats:** Phase 1 as designed here supports **Warp-Lab-signed extensions only** — the "community-contributed" half of M3.6's stated scope needs a signing-delegation or a review-and-co-sign workflow that this ADR does not design (explicitly deferred alongside the build itself). The advisory/block preflight tiers add a small amount of catalog-manifest schema surface (a `checkType` per validation rule) that doesn't exist yet anywhere in this repo's manifest schemas and will need its own schema review when built.
- **Naming hygiene:** any future implementation uses `extension`/`catalog` naming per M3.6's own ROADMAP language — no `poc`/`marketplace-beta`/`test-catalog` style framing (enforced by the existing `lifecycle-naming` ship-check).

## Alternatives considered

- **Copy the competitor's design as-is (curated DB rows + `dockerode` one-click installs against the host Docker socket).** Rejected: reopens the exact docker-socket-reachable-from-a-customer/LLM-facing-surface boundary THREAT_MODEL.md T5.3 explicitly accepts orchestrator RCE risk *by not having*. Would make a prompt-injected or socially-engineered agent session a path to arbitrary host container control.
- **A second, independent signing scheme for extensions (new keypair, new manifest format, new CLI) instead of reusing ADR-020's substrate.** Rejected: doubles the key-custody/rotation surface for no benefit — the trust problem ("is this artifact what we say it is, and is it untampered") is identical to the appliance-image problem ADR-020 already solved correctly (FIPS-clean ECDSA-P256, fail-closed verify, superset-trust rotation).
- **No RBAC gate beyond "authenticated" (any logged-in user can install).** Rejected: install is a host-mutating, resource-consuming, potentially tool-registering action — squarely inside the existing `requireRole("owner", "admin")` convention every comparable mutation in this repo already uses; a `guest`/`family` install path would be a regression relative to every other admin-surface route.
- **Build a thin Phase-1 slice now (e.g. just the manifest schema + verify command) instead of a pure docs ADR.** Rejected per the ticket scope: WARP-908 is explicitly docs-only, and M3.6 remains blocked on the OpenClaw sandbox contract regardless — a partial build would ship trust infrastructure with no consumer, ahead of its own dependency.
