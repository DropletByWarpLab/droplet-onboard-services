## What P4a builds

- **Schema.** `AccessPoint` (a door: name, `doorPositionSource ∈ {lock, dp1, none}`, held-open time, an explicit `active | retired` status) and `AccessEvent` (the §11.3 fourteen-value `kind`, append-only). Every state is an explicit enum column. `doorPositionSource = none` is a value, not a missing one.
- **Append-only in the database, not by convention.** A BEFORE UPDATE OR DELETE trigger refuses every UPDATE and every DELETE except inside the retention function (`access_event_purge`). A BEFORE INSERT trigger holds §9.7/§11.3: a `forced_door` or `held_open` row must reference a `door_open` row of the same door (a unique index allows one alarm of each kind per opening), and a door whose `doorPositionSource` is `none` can have no `door_open`, `door_closed`, `forced_door` or `held_open` row at all.
- **Door position and claims (§9.7)**, pure: a door's position from its newest event, and what a door may claim (a `none` door claims no forced-door or held-open alarm). Position turns `unknown` when link supervision lapses, and that ships with the supervision writer (P1 link): it is not aged out by the last event, because a device that reports only on change would read `unknown` after every close. It is also `unknown` after the owner changes `doorPositionSource`, until a report arrives under the new source: the old source's last word describes the old wiring. `AccessPoint.doorPositionSourceSince` records when the source last changed, an explicit column rather than a reading of `updatedAt`, which a rename also moves. The forced-door, held-open, relock and position-unknown derivations are **not built**: they have no caller until `services/access-control/` writes events. Their rules are recorded in `door-derivations.ts`. One must come back with a test when its derivation returns: held-open arms only after a grant or REX, never after `key_override` (§9.7).
- **Module `doors`**, registered in the App-Modules registry and feature-gated from day one, with a boot assertion that it is where it claims to be (§11.2).
- **Routes** under `/api/doors`: list doors, recent events (cursor-paged), and create / update / retire an `AccessPoint`. Reads are for owner and admin; writes are `owner` alone (§11.4) and never a service principal. Every change to a door is audited in the transaction that makes it, so a change the audit chain cannot record does not happen (503).
- **No chat tool.** The two reads, `doors_list` and `doors_recent_events`, were built in P4a and deferred to [P4b](#what-p4b-builds): while the module ships dark and module gating did not reach the chat pool (WARP-2972), a customer would have seen the product through the assistant. What P4a keeps is the §11.5 rule as a forward guard: any tool in the `doors_` namespace must be a read and must never unlock (`packages/tools-core/__tests__/doors-read-only.test.ts`).
- **Retention:** one daily purge at 03:55 on the cron runtime, `DOORS_EVENT_RETENTION_DAYS` days (365 by default), running whether or not `DOORS_ENABLED` is on — rows already written keep identifying people.
- **A boot assertion** (§11.2) that fails the start if the module is on and any list downstream of its descriptor is missing, including the append-only trigger in the database.

## What P4b builds

The dashboard page and the assistant's two read-only tools, in two changes: the page first, then the tools, once WARP-2972's module gate was on `stage` (WARP-3438 for both).

- **`/doors`** (`apps/web-dashboard`): the doors with each one's name, position **and when it reported it** ("Closed since 6:02 PM"), where the position comes from, and status; the recent-activity log with cursor paging; and, for the **owner alone**, add / change / retire. Admins read; the controls are not rendered for them, and a 403 that arrives anyway is a friendly toast that withdraws the controls for the visit. A position is never shown without its time, and a report with no time reads as unknown, never as current. A `none` door says plainly that Droplet can't tell whether it is forced open or left open (§9.7); a forced-door row says which claim it makes.
- **Nav, all three surfaces:** one row in Systems (owner/admin, module `doors`) and one Operations chip in the Workspace layout. The registry's `navHrefs` becomes `["/doors"]`.
- **Absent means absent, in the dashboard too.** `listedWhenUnavailable: false` removes the module from `GET /api/modules`, and the dashboard's gate reads "not in the payload" as "a module we can't classify: show it". For a module that ships dark that is wrong, so `ABSENT_UNLESS_LISTED` (`lib/dark-modules.ts`) names `doors` and reads absent as off, and its gate fails **closed** while the probe is unresolved: no nav entry and no page until the module list positively lists it. Off is a **plain 404** (`notFound()`, the page's own decision, since `ModuleRouteGuard` sits above the boundary and steps aside for these ids), not the guard's "isn't available" card: that card's "an owner or admin can turn it on" is untrue of a module only a flag switches on, and it would hint the product exists.
- **Copy** follows the Security rules and has its own lint (`components/doors/doors-copy.test.ts`): no monitor, alarm, secure, armed, "all locked" and the rest, and nothing that presents a position as current ("live", "right now", "currently").
- **Held-open time is not on the form.** It is stored (30 s by default) but nothing reads it until the derivation that arms held-open exists, so a control for it would advertise something that does nothing.
- **Two read-only chat tools**, `doors_list` and `doors_recent_events` (WARP-3438), back from P4a with the pieces that make them safe. Each guard is pinned by tests that go red when it is removed:
  - **Absent unless the module is on.** `doors` is a tool domain the `doors` module claims, so WARP-2972's one predicate withholds both tools from the chat pool, `/api/llm/tools` and MCP (`tools/list` and `tools/call`) whenever the module is off or absent, for an owner and a role-less person too. They no longer sit in `EXCLUDED_FROM_CHAT_TOOLS`: the module gate is what keeps them off a box without doors, and a `doors` selection rule brings them into a turn that asks about doors.
  - **Read-only at dispatch (§11.5).** The shared interceptor refuses any tool in the `doors_` namespace that is not affirmatively read-only, before the deny tier and beyond its reach (`denyTier.clear()` does not lift it, and a confirmation token minted for the exact call does not open it), including on the real mcp-server `CallTool` path.
  - **Bounded by the acting person (MCP).** The routes admit `_service:mcp` before any role check, so `doors` is an acting-user gated domain: the assistant reads doors only for a person who holds the module and whose tier the access catalog does not refuse (`refuseBelowFloor`: below admin). A family or guest person cannot ask for what their browser refuses.
  - **A position is the door's last report, with its time**: `doors_list` returns the position and when it was reported, and says an old position is not a current one; a door with no position source is `not_monitored`, never closed. `doors_recent_events` returns no paging cursor, only whether more exist.
- **The role builder still does not offer doors.** A safe deny, unchanged.

## Deviations from the brief, on purpose

- **Two tools, not four.** §11.5 lists four read tools. `doors_list` and `doors_recent_events` are built (P4b). The other two, `access_device_status` and `access_cell_health`, read models (`AccessDevice`, `Cell`) that belong to the service slice, so they are not built.
- **A trigger that covers DELETE.** The `SecurityEvent` trigger (ADR-059) covers UPDATE only and lets retention `DELETE` through by not being asked. Decision 3's retention and §11.3's "never updated" are both honoured here by covering DELETE too and giving the purge one sanctioned path: a plpgsql function that carries the bypass as a function-level `SET`, so the setting holds for exactly that call and is restored on the way out. No application code names it, and a source guard fails if any `.ts` file does.
- **Retention counts from receipt (`createdAt`), not from the device's `occurredAt`.** A device with a wrong clock must not be able to keep a row forever or expire it at once.
- **Corrections are not modelled.** §11.3 says a correction is a new row referencing the old one, but the fourteen kinds include no correction kind, so there is nothing to give that row. It waits for the service slice to say what a correction is.
- **Read floor is `admin`.** The brief asks for grants per door group and an emptied grant set denies (§11.4). Door groups and grants are out of scope, so until they exist the module's own grant is the only narrowing and the floor is set high. The floor is one fact stated in two places that a test holds equal: the role list the routes read (`services/doors-access.ts`) and the access catalog's `view` floor, which for doors is a refusal (`refuseBelowFloor`): a family or guest role cannot store `doors:view` at all, and one stored earlier grants nothing. The assistant's data hop reads the catalog's side (the MCP acting-user gate), so it is bounded by the acting person's tier. Widening to `family` is those two lines. The dashboard's role builder does not offer doors yet, which is a safe deny.
- **The access catalog offers `view` and nothing above it.** Door writes are the owner's and an owner holds every level through the §3 bypass, so a `manage` rung could only advertise a grant no non-owner can use. This adds `doors` to the one documented exception in the "admin ceiling is each module's top level" invariant (beside `team_chat`), pinned exactly.
- **The held-open time defaults to 30 s.** §9.7 names "the door's held-open time" and gives no number. It is a default the owner edits, not a spec value.
- **A strike-only door's unused grant stays outstanding until the door next closes.** There is no latch report there to say the strike re-secured, and the brief defines relock by state, never by a timer. It is part of why that claim is the weaker one. (A note for the derivation that lands with the service slice; nothing here derives it yet.)

## Cross-cutting negative suite (§14)

Applied now: no `doors_*` tool can unlock or write, and the dispatch refuses one that tries (the two real tools, and a synthetic writer, through the shared interceptor and the mcp-server); no `/api/doors` route lacks the RBAC grant; no in-place `AccessEvent` UPDATE or DELETE (against the trigger, on real Postgres); no forced-door or held-open claim on a `none` door (pure function and database); the module is absent when `DOORS_ENABLED` is off.

Deferred, with the reason: a UID accepted as a credential and an outside-lever turn registering as request-to-exit (no credential model, no device firmware — AC-017 and the firmware repo); a fail-safe device commissioned on cells (no `AccessDevice`); a lock that stops opening from the inside under any software state (a mechanical property, tested on hardware, P1/P3).

The two doors tools join none of the three: they read door positions and event times, and nothing writes door events yet (`services/access-control/` is a later slice), so there is no presence data for any of those paths to carry today. Whether doors joins them is Stefan / Romain's call, a line each, and it should be settled before that slice writes events or a box that uses a cloud model turns `DOORS_ENABLED` on, and certainly before a credential or grant model puts a person in the log (AC-017).
