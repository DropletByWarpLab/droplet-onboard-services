## §A — The new decision: the workshop run, the `workspace` domain, the store

A **workshop run** is an `AgentRun` whose tool pool is `core ∪ workspace`, started with `start_agent_run` (already Tier-2 — the person confirms that the box will spend minutes of compute) and attributed like any run. It is not a framework: the 2026-08-25 decision (the loop is the agent) and the 2026-09-04 rejection of a bundled agent framework both stand.

**The `workspace` tool domain** — every tool of which executes **inside `services/sandbox`** against one workspace volume and nothing else:

| Tool | Tier | What it touches |
|---|---|---|
| `workspace_read`, `workspace_search`, `workspace_diff`, `workspace_log` | read | the workspace checkout |
| `workspace_write` | write, no confirm | the workspace checkout — the blast radius is a volume |
| `workspace_run` | write, no confirm | a **bounded** command from an allowlist baked into the sandbox image (`npm test`, `npm run build`, `pytest`, `ruff`, `tsc`) — never a shell string; argv only |
| `workspace_commit` | write, no confirm | a commit on the working branch of one repo in the store, authored as the run's principal |
| `workspace_propose` | **Tier-2** | produces the draft artifact and stops the run — **the one call that makes something exist outside the sandbox**; `confirmationOwner: "interceptor"` |

Why writes inside the sandbox are Tier-1: ADR-047 §4.1's argument — a `transform` step _"shapes data between two steps that already have permission to move it"_. A workspace write changes a file that nothing on the box executes until promotion. Confirming every `workspace_write` would train the person to click through; confirming the one call that crosses the boundary is where attention belongs. Runs exclude non-confirming writes by Romain's rule; **`workspace_*` needs an explicit, tested exemption from that rule in `runToolPool()`**, next to the `send_notification` re-admission, covering only tools whose handler's route is the sandbox.

**The store** — bare repositories on a named volume (`workspace-git`), one per extension plus the templates repo, served over **smart HTTP** (`git http-backend`) behind the gateway with the existing session auth: read for any authenticated role, push for owner/admin and for the sandbox's service principal resolved to the _run's_ human at call time (never a system identity — the WARP-1580 rule). No forge (Gitea duplicates what the box does not need; Forgejo is GPL and out under the permissive-only rule; ADR-010's rejection stands). The box's own checkout is not the store; Warp Lab's repos are never mirrored into a customer's store; nothing in the store is ever pushed off the box by the box. The volume joins the backup set. Exporting a draft to Warp Lab is an operator download from the dashboard — the human carries it.

**The four invariants** (brief §3, verbatim — WARP-2896 implements a decision, not a brief):

- **I1 — The model never reaches the socket, a shell, or the LAN from a sandbox.** ADR-030's invariant restated. Every command a workspace run executes runs inside `services/sandbox` (§C), which mounts no socket, joins no LAN network and dials nothing.
- **I2 — Everything the model builds is a draft; a human promotion is the only thing that makes it exist.** ADR-047 §5.2's rule, extended from routines to connector profiles, extensions and toolsets. The promotion screen renders a readback **derived from the artifact** (its manifest, its steps, the registry flags), never from the model's description of it.
- **I3 — One tool universe, two layers, and nothing new is written into `TOOL_CATALOG`.** Desktop tools and extension tools register into the runtime layer through the WARP-2418 seam. `catalog.test.ts`'s completeness invariant keeps meaning "what is compiled into this box".
- **I4 — Every tool source we did not author is classified locally, defaults to `requiresWrite: true, requiresConfirmation: true`, and its self-description is never read.** ADR-043 §2, generalised: a desktop-hosted server and an extension are as untrusted as a vendor's server on the day they attach, and a _customer-written_ extension is the case where a name like `list_customers` is most likely to hide a write.

**What the model may build in v1:** an MCP server from a template in the store (`extensions/templates/`, TypeScript on the Node 20 baseline or Python 3.12) that composes box tools and shapes data. Not in v1: host services, host units, compose edits outside the fragment schema (§C), new profiles, new secrets, anything with egress, anything that runs as more than one process.

**Lifecycle, as the owner sees it:** `workshop run` → **draft** (a branch and a manifest in the store; visible with diff, test output and the derived readback) → **promote** (owner, Tier-2) → **signed** → **installed** (running, attached, tools blocked until classified or explicitly admitted) → **live** → **disabled** / **uninstalled**. Every transition writes the signed `tool_call` / `tool_run` activity rows runs and routines already write; no new activity kind.

## §B — ADR-014 amendment: the desktop shell hosts MCP servers on the PC

- **Status of this section:** **Proposed.** It becomes **Accepted** on Romain Jouffret's approving review of the PR that lands this file — his approval _is_ the acceptance, exactly as WARP-351 was for ADR-014 — while the rest of this ADR stays Proposed. If that PR merges without his approval, this line stays as written, [WARP-2901](https://warp-lab.atlassian.net/browse/WARP-2901) stays blocked (its AC names _"the ADR-014 amendment … Accepted"_), and the PR body names the follow-up PR that flips it.

ADR-014's _How to apply_ says: _"New client tools beyond the V1 catalog require an ADR amendment (catalog is a closed whitelist for V1)."_ This is that amendment, and it relaxes the rule **only** for tools that enter through [WARP-2426](https://warp-lab.atlassian.net/browse/WARP-2426)'s classification record. Nine native tools are not "agentic into the desktop"; what people mean by that is _the assistant working in my apps and my files_, and Warp Lab cannot write a Rust handler for every application on every customer's machine. The desktop shell becomes an **MCP host**: it launches local stdio MCP servers installed on that PC — a folder-scoped filesystem server, an application's own MCP server where the vendor ships one, the on-prem connector halves of WARP-2105 — and advertises their tools in `client-hello` exactly as it advertises `open_file` today.

What does **not** change, line by line:

1. **Per-tool consent stays default-`block`.** A newly hosted server's tools appear in the tray's AI-permissions surface as blocked; the person enables each one; pairing still grants presence, never capability.
2. **Classification is local and defaults to `write + confirm`** (I4). The shell relays a server's tool list; it does **not** relay `readOnlyHint` / `destructiveHint`, and the box refuses them if it does. Demotion to read-only is an owner action in WARP-2426's record.
3. **A deny class, enforced by the box, not by trusting the server's name.** Anything shaped like arbitrary execution, keystroke injection, screen capture or clipboard read is Tier-3 until [WARP-549](https://warp-lab.atlassian.net/browse/WARP-549) — expressed as a classification-record rule the owner **cannot override**, and tested against a fixture server that lies about what its tools do.
4. **Names are namespaced by server and device** — `<server>.<tool>__<device>` — so two PCs with the same server never collide, and the `mac` / `mac_2` prefix trap from WARP-354 is asserted for the new layer too.
5. **Budget.** A hosted server can advertise fifty tools. Hosted-server tools get a domain stamp with source `operator` and are selected per turn like everything else — never always-on.

The tier and consent decisions in ADR-014 were Romain's (WARP-351); this section needs the same sign-off and is not a slice anyone starts from the brief alone. [WARP-2105](https://warp-lab.atlassian.net/browse/WARP-2105) is answered by this section (Q4): the Windows-side connector agent is the same binary; the QuickBooks Web Connector track (WARP-2108 / WARP-2186, LAN-side inbound) is a separate decision this ADR does not take.

## §C — ADR-030 revision: the sandbox contract, a box-local key, processes before containers, and the stale blocker removed

ADR-030 D4 gated the build on _"the sandbox-execution contract with `inference-engine` (OpenClaw)"_. That component was deleted from `droplet-local-LLM` on 2026-04-30. The contract was unowned; this section owns it, and the same PR rewrites `ADR-030:46`, `:48`, `:62` and `docs/ROADMAP.md` M3.6 to point here.

**The sandbox contract ADR-030 said was missing is the apply-path fragment schema** ([WARP-2898](https://warp-lab.atlassian.net/browse/WARP-2898)): the OTA helper accepts an `ext-<id>` service under a **schema allowlist** — `image@sha256`, an allowlisted `environment`, `mem_limit` / `cpus` / `pids_limit`, `networks: [droplet-internal]`, `read_only`, `cap_drop`, `security_opt`, one named volume — and refuses any other key (`ports`, bind `volumes`, `privileged`, `network_mode`, `devices`, the socket). The helper's input domain widens from first-party release manifests to owner-signed extension manifests, which is exactly why every fence on it (verify in front of the socket, argv only, no LLM reachability) is preserved, not relaxed — ADR-030's own words.

**`services/sandbox`** ([WARP-2895](https://warp-lab.atlassian.net/browse/WARP-2895)) is one service with two customers — routine `transform` / `when` steps (ADR-047 §4, re-homed) and workshop runs — because two sandboxes with two hardening tables is how one of them drifts. Non-root; `read_only: true`, `cap_drop: [ALL]`, `security_opt: no-new-privileges`; tmpfs `/tmp` and the workspace volume as the only writable mount; `mem_limit` / `cpus` / `pids_limit` from a `SANDBOX_*` budget (a running v1 extension process draws from the same ceiling); **the first `internal: true` network in the compose file** — orchestrator ↔ sandbox only, no LAN membership, no WAN, no `network_mode: host`, reviewed on its own (WARP-2922); one process per run or per extension, killed on completion; dual timeout (service **and** caller); output cap reported when hit, never silently sliced; Node 20, Python 3.12 and git baked in, nothing installs at runtime; **no egress registration** — that is the honest reason customer-written code is safe to run; **no Docker socket**, not `:ro`, not on any profile.

**A box-local extension key joins ADR-020's superset-trust set.** ADR-030 reuses ADR-020's ECDSA-P256 substrate. Add one key: a **box-local extension key** held by `device-identity-svc` (TPM-sealed where the hardware has one; distinct from the device-identity key), which signs a manifest **only** inside the promotion route — owner role, Tier-2 confirmation, the readback shown. Its `usage: extension` is in the manifest schema and checked by `verify`: an extension key cannot sign a _release_ manifest; Warp Lab's key still signs the catalog and first-party extensions; a manifest signed by neither is refused.

**Phasing — processes first (v1, [WARP-2900](https://warp-lab.atlassian.net/browse/WARP-2900)), containers second (v2, WARP-2898).** v1: an extension is a directory in the store; promotion checks out the tagged tree into the sandbox's read-only extension mount; the sandbox runs its entrypoint as a long-lived supervised process on the internal network, speaking MCP over streamable HTTP to the orchestrator and nothing else — no image, no builder, no registry, no compose fragment, no socket path, no OTA apply. v2, when an extension needs its own image: a rootless BuildKit service on the internal network, an on-box OCI registry (`expose:` only, volume-backed), and the fragment through the apply path. Building on Warp Lab's CI is rejected: the box never fetches (ADR-045), and shipping a customer's source off the box is an egress decision the customer did not make.

**Attach.** A running extension is an MCP server; the orchestrator attaches it through the multiplexer and `registerServerTools` — the same code path as a remote vendor server — with a session profile generated from the manifest. Its tools land in the runtime registry with domain source `operator`, go through the classification record (§D) and become selectable per turn. `/tools` shows them under an **Extensions** section that reads the runtime layer. Install / disable / uninstall live in the admin console (WARP-2782), owner-only in v1 (Q2). An extension that needs box data gets a scoped service token (`SERVICE_TOKEN_EXT_<id>`) on the existing ladder, and the routes it reaches resolve the _installing owner_ as the acting human — 403 when nobody resolves, never an empty 200. An extension never holds egress.

ADR-030's D1–D3 stand unchanged; D4's first gate is replaced by this section; its vocabulary (`extension` / `catalog`, never a "poc"- or "-test"-style framing) is this ADR's too.

## §D — ADR-043 generalisation: desktop-hosted and extension servers are vendors' servers

ADR-043 §2 — _"Tool classification is a local, operator-owned policy table — never the wire"_: a newly discovered remote tool enters the table as `requiresWrite: true, requiresConfirmation: true` regardless of its name, description or annotations; demotion is explicit human review; a tool absent from the table is not callable; `readOnlyHint` / `destructiveHint` are never read — **applies to desktop-hosted servers ([WARP-2901](https://warp-lab.atlassian.net/browse/WARP-2901)) and extension servers ([WARP-2900](https://warp-lab.atlassian.net/browse/WARP-2900)) exactly as to a vendor's.** The record is [WARP-2426](https://warp-lab.atlassian.net/browse/WARP-2426)'s; it gains a `source` the reviewer can see (vendor / desktop / extension) and nothing that weakens the default for any of them.

ADR-043 §5 — _"The orchestrator process MUST NOT open a session to a remote MCP server"_; the socket lives in a `web-fetch`-shaped component between the server and the orchestrator, gate → cache → upstream, an audit row per outcome — **applies to both new sources.** For a desktop-hosted server the component is the shell on the PC (the box dials nothing inbound; the shell relays over the existing MQTT dispatch); for an extension it is `services/sandbox` on the internal network. In neither case does orchestrator product code gain a remote transport import.

A one-line note in ADR-043's Follow-ups points here.

## Consequences

- **Positive.** The epic's eleven slices implement decisions rather than a brief. The extension build is un-gated from a component that no longer exists and re-gated on a contract this repo owns (§C). Three security properties are stated once and inherited by every new tool source: default `write + confirm` (I4), no wire-supplied privilege, no socket / shell / LAN from a sandbox (I1).
- **Cost.** One more service and the repo's first `internal: true` network (Q7, reviewed alone). A second signing key in the superset-trust set, with a `usage` field `verify` must check. An exemption in `runToolPool()` that must be tested to cover only sandbox-routed tools.
- **What this ADR does not decide.** WARP-2175 (the repo rename), WARP-1955 (updater custody), WARP-2105's LAN-inbound Web Connector half (WARP-2108 / WARP-2186), and the reopening of WARP-355 (a workflow edit, WARP-2913). It cites each by key.
- **Vocabulary.** `extension`, `catalog`, `workshop run`, `notifier`. Enforced on this PR by a grep of the added `docs/` lines for the four tokens WARP-2912's AC names, returning nothing; `ship-check.sh lifecycle-naming` never walks `docs/` and is not the gate.
