# ADR-061: Native Linux client — Rust, GTK 4 and libadwaita, no web view

- **Status:** Proposed (2026-09-25)
- **Sibling of:** ADR-062 (native per-platform desktop clients: the native WinUI 3 Windows client and the macOS row; PR #2444, WARP-3211). Not ADR-060, which is the Windows Hello relying party. The clients deliberately share no code (ADR-008 §1). The Windows client is tracked under epic WARP-3223 and described in `droplet-windows` (`docs/DESIGN.md`, `docs/ARCHITECTURE.md` on `main`).
- **Ticket:** WARP-3203.
- **Supersedes for desktop Linux:** ADR-009's desktop direction, as its Win .exe row states it: "wrapping the dashboard's React build". ADR-009 never listed Linux, so this ADR is the Linux row, and ADR-009 carries a pointer here above its Clients table.
- **Amends:** ADR-037 (tunnel key custody), by one recorded exception for Linux (Decision 7). ADR-037 carries a pointer here after its per-platform table.
- **Builds on:** ADR-008 (native clients implement the contract themselves), ADR-023 and ADR-058 (trust: public certificate, else the pairing's pinned key, never TOFU), ADR-037 (tunnel key custody), ADR-045 (the operator stages installers; the box never fetches).
- **Repo:** [`DropletByWarpLab/droplet-linux`](https://github.com/DropletByWarpLab/droplet-linux), first PR [droplet-linux#1](https://github.com/DropletByWarpLab/droplet-linux/pull/1). CI builds, tests and screenshots the real app against a stand-in box on Ubuntu 24.04.

## Context

When this ADR was written no Linux client existed, and `data/app-downloads/EXPECTED` still says so (`linux absent - no Linux client exists`). The first client has since landed: [droplet-linux#1](https://github.com/DropletByWarpLab/droplet-linux/pull/1) merged 2026-09-26. No signed or staged installer exists yet; droplet-linux CI builds an unsigned `.deb` (the `droplet-deb` artifact) but nothing signs it or stages it. The staging pipeline already accepts `.deb`, `.rpm` and `.AppImage` for a `linux` platform (`scripts/app-downloads/stage.mjs`), and the device-clients platform list already names `linux`.

Stefan asked for a fully native Linux app, explicitly not a web view, on 2026-09-25. In the same stretch the Windows client moved from Tauri + WebView2 to native WinUI 3: the roadmap is dated 2026-09-25 and Stefan decided the direction on 2026-09-26 (epic WARP-3223, decided in ADR-062). ADR-009's reason for the web-view shell was "don't reimplement every page". That is now outweighed by what a wrapped dashboard can't do well: pinned trust inside the web view, native notifications, keyring custody, the system VPN, and a UI that belongs on the desktop it runs on.

## Decision

1. **Stack: Rust, GTK 4, libadwaita.** These are platform widgets and the GNOME HIG, and they run on KDE too. Rust is the language the Tauri Windows shell's trust (`trust.rs`) and LAN discovery (`lan_discovery.rs`) were proven in, so those rules are ported with their fixtures rather than re-derived. The floor is **GTK 4.14 / libadwaita 1.5 (Ubuntu 24.04 LTS)**.
2. **No web view, anywhere.** A surface is native, or it isn't in the sidebar. "Open the full dashboard" opens the system browser for everything not yet native, and only when the box presented a public certificate chain **and** its FQDN resolves locally to a live box. This is ADR-062 row 3, adopted unchanged. On a pinned-key pairing (Decision 4) the browser would meet the box's own certificate with no pin to check it against, and a pinned certificate is trusted only inside the app. So the app says, in finished copy, that the section needs the web dashboard, which this PC cannot open yet. That message is the only stand-in. There is no "coming soon" page.
3. **No shared library with other clients** (ADR-008 §1). The contract is the orchestrator's `stage` routes. `droplet-kit` and the iOS app are the behavioural reference. If duplication hurts, the sanctioned next step is OpenAPI codegen, not a shared crate.
4. **Trust is ADR-058 §2.0 exactly.** It uses rustls with the bundled Mozilla roots, never the OS store. When the public chain fails, the pairing link's `spki=` pin is accepted for hosts the leaf's SAN names, inside its validity window. There is no TOFU. A key mismatch is a loud "this isn't the Droplet from your link". The pin is per pairing, not per host, because it is the box's identity. Discovery (mDNS `_droplet._tcp` and `_https._tcp`, the friendly names, certificate-SAN discovery of `<name>.droplet-us.com`) changes where the app looks, never what it trusts.
5. **Links.** `droplet://` is registered as `x-scheme-handler/droplet`. A pair link may choose the box only on a fresh client (WARP-3035). `overlay-enroll` links are never actioned from the desktop (WARP-1477).
6. **Secrets.** Session tokens go to the desktop keyring (Secret Service). With no keyring they are memory-only and the app says so. They are never written to a file. The pairing record (address, pin, box name, and the remote-access connection's UUID and plan) is not secret and lives in `~/.config/droplet/pairing.json` (0600). Only pairing and "Forget this Droplet" write the address and the pin.
7. **Remote access goes through NetworkManager's WireGuard.** The tunnel comes up only when the LAN probe fails (the mobile clients' D1 rule). **Recorded exception to ADR-037's custody rule, for Linux:** NetworkManager owns the tunnel. The app generates the WireGuard keypair, hands the private key straight to NetworkManager over D-Bus (stored root-only in its system connection), zeroizes its copy and never persists it. ADR-037 says the key is born in the tunnel owner and never leaves it: "The user-mode app never sees the private half." Linux does not meet that: the app holds the private half for the moment it takes to hand it over. So this is an exception, not an ADR-037 row that satisfies the rule. ADR-037 gives the rule's purpose as "never move a private key across a privilege boundary", and its Windows ban is on a user-writable file that feeds a privileged unit. Here nothing user-writable feeds NetworkManager: the key travels over D-Bus, never through a file, and the desktop user who runs the app is the user polkit already lets read and modify that connection. We treat that as Android's "same trust domain" case rather than Windows' split privilege. The exception holds only while the connection is bound to that user, so **the app creates it with `connection.permissions=user:<enrolling user>`** (the D-Bus setting is `user:<name>:`). NetworkManager allows a connection with empty permissions to every user, so an unbound connection could be brought up by any active local session and polkit may let other users modify it. On a business PC shared by several staff that would hand one person's enrolled tunnel to everyone on the machine. Enrollment binds to the paired box only (ADR-037, rogue-QR binding). **Forget this Droplet** deletes the NetworkManager connection (by the stored UUID) and revokes the peer on the box when it can reach it; failing that, it says the peer may still be enrolled.
8. **Distribution:** a `.deb` built in CI (`cargo deb`) and staged by the operator (ADR-045). `data/app-downloads/EXPECTED` moves `linux` from `absent` to `blocked` (with a ticket to be filed) until the first signed build exists, then to `installer`. Flatpak and `.rpm` come later and don't change this ADR.

## Consequences

- Linux ships Home, Ask AI, Files, Cameras, Network, Devices, Notifications, Remote Access and Settings natively in 0.1. The rest opens in the system browser until built (`droplet-linux/docs/PARITY.md`), subject to the gate in Decision 2.
- On a pinned-key pairing, Help and every browser-only section are unavailable, because the hand-off needs a public chain. The `open-dashboard` action in droplet-linux (`crates/droplet-app/src/window.rs`, `main` at `79bbc5ce`) opens the box's address with no such check today. This ADR requires the gate and does not build it; that is client work in droplet-linux.
- ADR-037's custody rule has one recorded exception, Linux (Decision 7). A later client that wants the same shape cites that exception and meets its conditions (a user-bound connection, no file between the app and the tunnel owner, the app's copy zeroized), or amends ADR-037.
- Remote Access follows the enrolling user's session. A connection bound to `user:<name>` (Decision 7) is usable only while that user has a session, so the tunnel does not come up before login. That matches the D1 rule: the app brings it up when the LAN probe fails, so no app session means no tunnel.
- Passkey sign-in (libfido2, the `webauthn` routes, RP = the box's name, never an IP) and native SSO (loopback PKCE on `/api/sso/oidc/native/*`) are the two sign-in extensions this client wants. ADR-063 (WARP-3226, #2446) decides the box side: the native SSO handoff, and the rule that the relying party comes from `Host` only (OBS-2, WARP-3229). It decides the client side for Windows only (`webauthn.dll`). **No ADR decides the Linux passkey client yet, and this one does not.** Its rules (user verification required, PIN handling, refusing an IP as `rpId`, authenticator-data checks) need their own decision before it ships. On `stage` today: the passkey routes serve native callers with `?return=body`, and the relying party comes from `Host` only (WARP-3229, #2448). Not on `stage`: the native SSO routes (WARP-3212, #2518, an open draft), and this ADR does not assume they exist. The same routes are meant to serve every desktop.
- ADR-056's "desktop as an MCP host" and ADR-014's desktop tool-host consent tiers apply to this client too. Neither is in 0.1. Both need WARP-1955-style signing and update custody decided for Linux before anything runs tools on a customer's PC.
- **Open, not decided here:** the app id. Linux uses `ai.warplab.Droplet`, matching Android's `ai.warplab.droplet` namespace, and Windows uses `ai.warp-lab.droplet` (ADR-062 row 10). ADR-045 already flags the iOS/Android bundle-id split, and this adds a data point, not a decision.
