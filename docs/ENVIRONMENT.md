# Environment variables — reference

The variables you'll most often need, with defaults and gotchas. The
**exhaustive, always-current list is [`.env.example`](../.env.example)**
— if a variable isn't in this table, look there. The safety-critical
rules (the `MATTER_*` ban, CORS exact-match semantics, rate-limit proxy
trust, PM secrets) are summarized in [`CLAUDE.md`](../CLAUDE.md).

> ⚠ **Never add new `MATTER_*` env vars.** matter.js scans `process.env` at startup and auto-imports every `MATTER_*` variable into its internal `VariableService`, dot-namespacing each one. Collisions with root-node behavior ids throw `UnsupportedCastError: Property "X" is unsupported` and break controller init. Use a `DROPLET_MATTER_*` prefix for our own env vars instead. `MATTER_STORAGE_PATH` is the only surviving `MATTER_*` name and is allow-listed by `scripts/test-security.sh`. Full rationale: [`apps/orchestrator/src/config.ts`](../apps/orchestrator/src/config.ts) — the block comment above the `Matter` schema section.

| Variable             | Description                                          |
|----------------------|------------------------------------------------------|
| `DATABASE_URL`       | PostgreSQL connection string. `?sslmode=require` is mandatory as of WARP-233 — the `db` service rejects non-TLS TCP (`docker/postgres/pg_hba.conf`). Nextcloud needs no param (libpq `sslmode=prefer` auto-upgrades). |
| `POSTGRES_PASSWORD`  | Main Postgres (`db` service) password                |
| `NEXTCLOUD_DATABASE_URL` | file-indexer's connection for Nextcloud file-id lookups (`oc_storages`/`oc_filecache`). Optional — defaults to `DATABASE_URL` with only the database name swapped to `nextcloud` (WARP-1327; never derived via `str.replace`, which mangled the username). The default role's read grants are applied by `setup.sh` on every run (WARP-1328); if you point this at a dedicated role (e.g. `indexer_ro`), grant it `CONNECT`/`USAGE`/`SELECT` on `public.oc_storages, public.oc_filecache` equivalently. |
| `REDIS_URL`          | Redis connection string. As of WARP-234 the `cache` service is TLS-only (`rediss://…cache:6380`; plaintext 6379 is closed) with per-service ACLs — the `.env` URL authenticates the ping-only `default` user; real clients get per-identity URLs from `docker-compose.yml`. |
| `REDIS_PASSWORD` | Password of the ping-only `default` ACL user (health probes, verification harness) |
| `REDIS_PASSWORD_ORCHESTRATOR` / `REDIS_PASSWORD_AI_GATEWAY` / `REDIS_PASSWORD_MCP` | Per-service Redis ACL identities (WARP-234). Generated by setup.sh; hashed into `data/secrets/redis/users.acl`. Nextcloud reuses `REDIS_HOST_PASSWORD` as the `nextcloud` ACL user. Runbook: [`docs/security/redis-tls-acl.md`](security/redis-tls-acl.md) |
| `MQTT_BROKER`        | MQTT broker URL (`mqtts://broker:8883` — WARP-235 mTLS; identity is the per-service client-cert CN, see `docs/security/internal-mtls.md`) |
| `MQTT_BROKER_LOCAL`  | Loopback TLS listener for host-network services (`mqtts://localhost:8883`) |
| `NEXTCLOUD_ADMIN_USER` / `NEXTCLOUD_ADMIN_PASSWORD` | Nextcloud admin account bootstrap |
| `JWT_SECRET`         | Orchestrator JWT signing secret (per-device; `change-me` placeholder in `.env.example`). **Production boot fails fast** (WARP-580) when it is under 32 chars or a known dev placeholder |
| `COMPOSE_PROFILES`   | Which optional service groups start (`linux`, `display`, `full`, `single-box`, `pm`, `eval`, `ops`, `docs`, `telemetry`). Written by `setup.sh` — semantics per shape in the `docker-stack` skill. `docs` (document engine — Collabora CODE by default, WARP-882/WARP-1686) is **opt-in / default-OFF** here: the operator adds it to `COMPOSE_PROFILES` and sets `DOCS_ENABLED=1` to run the ~2 GB engine (single-box `setup.sh` RAM-gates it ON above 8 GiB). `telemetry` (fleet-agent, WARP-963) is likewise **opt-in / default-OFF** and additionally gated by `DROPLET_TELEMETRY_ENABLED` |
| `AI_GATEWAY_URL`     | AI gateway endpoint                                  |
| `OLLAMA_URL`         | Chat-path Ollama endpoint (default `http://host.docker.internal:11434` locally). Points **direct at Ollama**, not the manager's `/proxy` — see the `debug-ollama-call-path` skill |
| `INFERENCE_MANAGER_URL` | Optional model-lifecycle-manager root for lifecycle/limits, decoupled from the chat `OLLAMA_URL` (XR-05). If `OLLAMA_URL` itself ends in `/proxy`, the manager root is derived from it. **Renamed from `OLLAMA_MANAGER_URL` in WARP-1748** — WARP-1743 made that service runtime-agnostic (`INFERENCE_RUNTIME` picks the backend; `ollama` is just the default), so the `OLLAMA_` prefix named an implementation detail rather than the contract. Unrelated to `OLLAMA_URL` above, which is the **chat** endpoint and is deliberately unchanged |
| `OLLAMA_MANAGER_URL` | **Deprecated** — the pre-WARP-1748 name for `INFERENCE_MANAGER_URL`. Still read as a fallback so the `.env` on an already-deployed box keeps sizing its limits; the ai-gateway logs a warning naming the old var, the new var, and the `.env` to edit. `INFERENCE_MANAGER_URL` wins when both are set (an explicitly-empty value counts as unset, so a compose `${VAR:-}` blank can't shadow a working legacy value). Rename the line rather than keeping both. The fallback is removed in a future ticket once every provisioned box has migrated — same lifecycle as ADR-011's `JETSON_OLLAMA_URL` → `OLLAMA_URL` rename |
| `OLLAMA_CONTEXT_LENGTH` | Context window (tokens) for the bundled single-box Ollama (default `16384`). Ollama's own default is 4096, which the owner-role tool schemas alone overflow — symptom: instant empty chat answers (WARP-854). **WARP-1118 §10:** the **orchestrator** reads the same value (`config.OLLAMA_CONTEXT_LENGTH`) and its request-size estimator (`context-budget.service.ts`) budgets the assembled request (system blocks + serialized `tools[]` + pins + attachments + history) against `OLLAMA_CONTEXT_LENGTH − 1024` (output reserve). When it would overflow, the orchestrator deterministically drops the business block, then the persona block, then falls to history/attachment trimming — *preventing*, not just detecting, the overflow. Keep the compose `ollama` and `orchestrator` services on the same value so the estimator's window tracks the model server's actual window (both are wired to this one env token). Configures the window only — it is **not** a model swap and does not touch the One-Model Rule. |
| `OLLAMA_FLASH_ATTENTION` / `OLLAMA_KV_CACHE_TYPE` | Window-experiment levers on the bundled `ollama` service (agent-budgets spec §5). Both default unset (today's behavior — f16 KV cache, no flash attention). `OLLAMA_KV_CACHE_TYPE=q8_0` roughly halves KV-cache VRAM, buying window headroom on the 16 GB single-box GPU; `OLLAMA_FLASH_ATTENTION=1` is its prerequisite. Leave both unset until the spec §6 phase-1 window-sweep measurement (16k → 24k → 32k-with-q8_0) picks values — a config that spills KV to CPU is rejected on latency grounds before any eval time is spent. |
| `INFERENCE_RUNTIME` | Which inference runtime the box serves from: unset/`ollama` (default) or `dmr`. **One reader in this repo** — ai-gateway's capability layer (`providers/ollama_local.py`), read at module IMPORT: under `dmr` the static capability table becomes the gap-filler for DMR's missing `/api/show` `capabilities` array; without it every model silently reports `tools=false`. Changing it requires `--force-recreate` of ai-gateway (a `docker restart` re-reads nothing). Set by `scripts/dmr/flip-single-box.sh` in BOTH env files, never by hand; `scripts/lib/single-box.sh` READS it so a setup re-run cannot un-flip the runtime wiring. |
| `LLM_MODEL` | The one serving model (One-Model Rule). Under Ollama: `name:tag` (`gpt-oss:20b`). Under DMR it must be the EXACT registry-qualified string `GET /api/tags` reports (e.g. `docker.io/ai/gpt-oss:20B-F16`) — the readiness pull-guard compares raw strings, so any other spelling re-pulls the full artifact on every orchestrator boot. Derived live by the flip script, preserved by setup re-runs when `INFERENCE_RUNTIME=dmr`. |
| `OLLAMA_CHAT_PATH` | Chat-completions path on the local runtime (default `/v1/chat/completions`). Correct for BOTH Ollama and DMR — DMR serves the bare `/v1` path (measured; the `/engines/v1` prefix is optional). Leave unset. |
| `DMR_IMAGE` / `DMR_PORT` / `DMR_CONTEXT_LENGTH` / `DMR_MEM_LIMIT` / `DMR_CPUS` / `DMR_PIDS_LIMIT` | Knobs on the **dark** `dmr` service (WARP-1772 — Docker Model Runner as the second ADR-036 runtime backend, profile `dmr`, never default). Nothing reads them until an operator activates the profile, and activating the profile still changes no serving path — the flip is WARP-1749/WARP-1772 phase 2, hard-gated (soak + `size_vram` product decision + human sign-off; see `docs/dmr-single-box.md`). Defaults: pinned `docker/model-runner:v1.2.6-rocm`, loopback `12434`, context `16384` via `LLAMA_ARG_CTX_SIZE` (WARP-854 parity — the env form provably applies and survives restarts, unlike the `_configure` endpoint, which 202s-then-ignores short model ids; ADR-036 §5a), and `ollama`-matching resource caps (`4g` / `4.0` / `2048` — the 4g cap is inherited reasoning, unverified under DMR's 20B staging; re-measure before any flip). |
| `AGENT_MAX_ITER_DEFAULT` / `AGENT_MAX_ITER_CAP` | Agent-loop step limit (agent-budgets spec §1) — the default iteration count a turn uses when the caller doesn't set `max_iter`, and the hard cap no caller (including an explicit `max_iter`) can exceed. Both enforcement points (the `llm-agent.service.ts` clamp and the `routes/llm.ts` zod bound) read the same config values so they can't drift. Defaults `10` / `10` — the default was raised from 5 by the 2026-07-21 staging step-sweep measurement (`staging-seed/eval/findings-2026-07-21-tuning.md`: 23/36 twice-confirmed at 10 vs 21 at 5; typical turns still finish in ~3.6 iterations so there is no latency cost on easy turns). If `AGENT_MAX_ITER_CAP` is configured below `AGENT_MAX_ITER_DEFAULT`, boot clamps the default down to the cap and emits a structured warning. |
| `AGENT_BLANK_TURN_DEBUG` | WARP-1479 — when a turn ends with **no visible answer**, the orchestrator logs a `blank_final_answer` line attributing the blank to its layer (`model_returned_nothing` / `reasoning_only` / `sanitizer_demoted_json` / `sanitizer_stripped_all`) with character counts and the turn's tool-call count. Those counts and labels are always logged. Setting this to `1` additionally includes a bounded 500-char excerpt of the **raw** model completion — off by default because that text can quote the user's own documents. Turn on for a debugging window, then off again. |
| `TOOL_SELECTION_MODE` | Relevance-based tool advertisement (agent-budgets spec §3). Values `off` (default, ships today) / `domains`. `domains` narrows each turn's advertised tool schemas to a core set (`search_content`/`read_file`/`list_files`/memory-read) plus keyword-rule-matched `ToolDomain` groups plus domains of tools already called this conversation, instead of advertising the full chat-scope pool every turn — the WARP-642 self-heal guard re-admits a wrong guess's whole domain at the cost of one lost iteration, never a failed turn. Kill switch: set back to `off` to restore full-pool advertisement. Ships `off`; flipped per-deployment for the spec §6 phase-3 measurement, which decides the shipped default. |
| `RAGAS_OLLAMA_URL` | OpenAI-compat `/v1` base URL the rag-eval (RAGAS) judge calls (default `http://host.docker.internal:11434/v1` — suits mac/dev where Ollama runs on the host). On the single-box shape `setup.sh` (`single-box.sh`) overrides it in `.env` to `http://ollama:11434/v1`: the bundled `ollama` container publishes only `127.0.0.1:11434` on the host, and a loopback bind is unreachable from the bridge-gateway IP on Linux, so the default would `ECONNREFUSED` every judge call. |
| `RAGAS_EVAL_USER` | Which user's indexed corpus the appliance RAGAS eval searches — the runner passes it as `?user=` on every `/api/admin/retrieval-eval/search` call, because the rag-eval service principal owns no files of its own. **No default** — the operator sets it deliberately in `.env`; until it is set, runs fail fast with `eval_user_required` instead of scoring an empty corpus into the baselines. |
| `BUSINESS_PROFILE_REVIEW_ENABLED` | WARP-1122 — daily business-profile refresh-nudge check (03:30, advisory-locked). **Explicit boolean** (`true`/`false`/`1`/`0`, default `true`) — enabled-ness is never derived from `BUSINESS_PROFILE_REVIEW_DAYS` being unset (§5-11). When enabled and the completed profile's `updatedAt` is older than the review window, `reviewNudgeState` flips to `due` and the chat empty state shows the dismissible "It's been a while" chip. |
| `BUSINESS_PROFILE_REVIEW_DAYS` | WARP-1122 — the review window in days (default `90`, non-negative). A dismissed nudge only re-arms once the dismissal itself is older than a full window (never resurrects within the same review period). An explicit `0` is honored (staleness cutoff becomes "now", so a completed profile nudges on every daily check — useful for verifying the nudge). |
| `VISION_MODEL` | Preferred LOCAL vision model for chat image attachments. When the selected chat model can't see an attached image, the orchestrator auto-routes that turn to this model and model-readiness pulls it at startup (like `LLM_MODEL`). Unset → no local vision; cloud vision (gpt-4o / Claude) still works by selecting a cloud vision model explicitly. |
| `VISION_MAX_IMAGES` | Max images re-sent per chat request (most-recent-first), bounding token cost on a small local context window (default `3`, range 1–8). |
| `EMAIL_SENDING_STALE_MS` | Grace window (ms) before an outbound email draft stuck in `sending` is reconciled to `failed` (WARP-890). A draft is claimed `queued→sending` before the SMTP send; if its terminal status callback never lands (email-indexer crash / lost PATCH) it would strand in `sending`. Both the orchestrator's stale-sending cron (every 5 min) and the email-indexer's outbound tick sweep `sending` rows whose `claimedAt` is older than this window to `failed` (never re-queued — the send may have completed). Default `600000` (10 min). An explicit `0` is honored (reconcile immediately — useful in tests). |
| `DROPLET_FIPS_MODE` | Per-customer FIPS 140-3 activation (WARP-318). **Default `0` (OFF)** — modern crypto, identical to a non-FIPS install. `1` boots all five services FIPS-enforcing against the in-image validated provider (CMVP #4282, WARP-967); **no rebuild**. Flip via `setup.sh --fips` / `--no-fips` (explicit boolean, never derived). setup.sh derives `OPENSSL_CONF`, `DROPLET_FIPS_REQUIRED`, `NODE_OPTIONS`, `PG_SSLMODE`, `PG_HBA` (+ the `DATABASE_URL` `sslmode` param) from it — do not hand-edit those (`OPENSSL_MODULES` is actively removed: WARP-1063, see `docs/fips.md`). FIPS RESTRICTS algorithms; it does not add strength. Full guide: [`docs/fips.md`](fips.md) |
| `DROPLET_SSO_{GOOGLE,ENTRA,OKTA}_{ISSUER,CLIENT_ID,CLIENT_SECRET,REDIRECT_URI}` | Optional OIDC SSO provider config (commented out by default in `.env.example`) |
| `DROPLET_TELEMETRY_ENABLED` | Master opt-in for the fleet-agent's portal telemetry (WARP-963). **Default OFF**; only `1`/`true` enables. Even when the `telemetry` compose profile starts the container, the process idles with ZERO egress unless this is set AND credentials exist (`DROPLET_TELEMETRY_PROVISIONING_CODE`, or the identity persisted on the `fleet-agent-state` volume by a prior registration). Full var list + egress-audit table: [`services/fleet-agent/README.md`](../services/fleet-agent/README.md) |
| `DROPLET_TELEMETRY_PROVISIONING_CODE` | One-time register code minted in the analytics portal's `/settings/tokens`. Consumed on first successful `/agents/register`; the returned ingest token is stored ONLY on the fleet-agent's runtime state volume — never in `.env`, never tracked |
| `DROPLET_UPDATE_POLL_ENABLED` | Opt-in for the fleet-agent's signed update-poll (WARP-1025, the ratified ADR-028 mount). **Default OFF**; only `1`/`true` enables — a consent separate from `DROPLET_TELEMETRY_ENABLED` (either half runs without the other, same container). Polls the GitHub Releases manifest every `DROPLET_UPDATE_POLL_SEC` (default 300 s), verifies the cosign signature against the baked-in trust anchor (fails closed on the WARP-535 placeholder until the key ceremony), applies the ADR-028 tag-selector targeting, and records/reports the candidate — never applies. Targeting tags + full var list (`DROPLET_OTA_RELEASES_URL`, `DROPLET_OTA_GITHUB_TOKEN`, `DROPLET_UPDATE_CHANNEL`, `DROPLET_CUSTOMER`): [`services/fleet-agent/README.md`](../services/fleet-agent/README.md) |
| `DROPLET_HOST_ROOT` | Absolute host path of this checkout, written by `setup.sh` on every run (WARP-1669). The OTA apply path needs it because the orchestrator runs `docker compose -f "$DROPLET_OTA_COMPOSE_FILE"` from INSIDE its container against the HOST daemon: the compose CLI reads the file locally while the daemon resolves that file's relative bind mounts (`./certs`, `../data/secrets/…`) on the host, so the path must be identical in both places. `docker-compose.yml` derives `DROPLET_OTA_COMPOSE_FILE`, `DROPLET_OTA_CONFIG_ROOT`, and the orchestrator's config-tree mount from it. Don't hand-edit — move the checkout and re-run `setup.sh`; a stale value makes Docker create the missing host paths as EMPTY directories and the stack restarts without its certs or secrets |
| `DROPLET_OTA_APPLY_SCRIPT` | Absolute path to `apply-update.sh` as mounted in the orchestrator container. **Empty (default) DISABLES the OTA apply window** — the box still polls and tracks pending releases but never swaps containers. Correct posture for dev laptops and CI |
| `DROPLET_OTA_CONFIG_ROOT` | Where a release's `configs.tar.gz` is extracted. Defaults to `DROPLET_HOST_ROOT`, i.e. the REPO ROOT — CI packs configs as `docker/…` (`git archive HEAD docker`), so extracting into the compose file's own directory nests them one level too deep and the update silently changes nothing (WARP-1669). Override only for layouts that don't put the compose file one level below the packed root |
| `FILES_ROOT`         | `.data/files` (local) / `/data/files` (Docker)       |
| `STORAGE_BACKEND`    | `legacy` or `nextcloud`                              |
| `NEXTCLOUD_URL`      | Nextcloud instance URL                               |
| `DOCS_ENABLED`       | EXPLICIT master switch for in-browser viewing/editing/co-authoring (WARP-882/WARP-1686). **Default `1` (ON) on ≥32 GB boxes** — `setup.sh` (`single-box.sh`) writes `DOCS_ENABLED=0` on ≤8 GB boxes. Operator sets `1`/`true` AND adds `docs` to `COMPOSE_PROFILES` to run the ~2 GB engine. NOT derived from `DOCS_INTERNAL_URL` emptiness |
| `DOCS_ENGINE`        | WHICH document engine runs behind the `docs` profile (ADR-034): `collabora` (default — Collabora CODE, LibreOffice technology, **no licensing fee**; connector app `richdocuments`) or `onlyoffice` (OnlyOffice DS CE, AGPLv3 — OEM license required to ship; connector app `onlyoffice`). Drives the orchestrator probe/editor URL, the gateway `/docs/` proxy variant, and the `nextcloud-init.sh` connector branch |
| `DOCS_ENGINE_IMAGE`  | The engine container image; MUST track `DOCS_ENGINE` (`collabora/code:26.04.2.4.1` / `onlyoffice/documentserver:8.2`). `single-box.sh` writes the trio together so they never diverge |
| `DOCS_INTERNAL_URL`  | Compose-network base URL the orchestrator probes for the engine's health; tracks `DOCS_ENGINE`: `http://docserver:9980/docs` for collabora (coolwsd port + `net.service_root`), `http://docserver` for onlyoffice. Empty → engine treated as unavailable |
| `DOCS_EDITOR_PUBLIC_PATH` | Public path the gateway fronts the engine on (nginx `location /docs/`); default `/docs/` |
| `DOCS_ACCESS_TOKEN_TTL_SECONDS` | Per-session editor access-token TTL in seconds (default `1800` = 30 min); the dashboard refreshes before expiry |
| `DOCS_MEM_LIMIT` / `DOCS_CPUS` / `DOCS_PIDS_LIMIT` | `docserver` container resource ceilings (ADR-021; defaults `2g` / `2.0` / `1024`). ~2 GB additive |
| `NEXTCLOUD_PUBLIC_PATH` | Browser-facing path the gateway fronts Nextcloud on (nginx `location /nextcloud/`; default `/nextcloud`). Used for the editor URLs the dashboard iframe loads — `NEXTCLOUD_URL` is compose-internal and unreachable from a browser (WARP-1686) |
| `ONLYOFFICE_JWT_SECRET` | Shared HS256 secret the OnlyOffice engine, the Nextcloud `onlyoffice` connector, AND the orchestrator's editor-session tokens sign/verify with. **Still required under `DOCS_ENGINE=collabora`** (the orchestrator signs session tokens with it; Collabora itself trusts via its aliasgroup WOPI-host allowlist instead). Per-device; **generated by `setup.sh` (`openssl rand -hex 32`)** into `.env` — empty placeholder in `.env.example`, never `change-me`. Empty → the orchestrator treats the doc-server as unavailable (fail-safe: no forgeable default-secret JWTs). **License note (ADR-034):** the default engine has no fee; an OnlyOffice OEM/commercial license is required only when shipping `DOCS_ENGINE=onlyoffice` |
| `ONLYOFFICE_JWT_ENABLED` | Whether the OnlyOffice engine enforces the JWT (default `true`; matched by the connector; ignored by Collabora) |
| `SMB_ENABLED` | EXPLICIT master switch for the network-drive surface (the SMB "Droplet" share in Windows Explorer / macOS Finder — `docs/network-drive.md`). Written by `setup.sh`: `1` on Linux (where the `linux` compose profile starts the `samba` service), `0` on macOS dev hosts. NOT derived from `SMB_PASSWORD` emptiness. Read by the orchestrator's `GET /api/storage/network-drive` |
| `SMB_PASSWORD` | Device-wide credential for the fixed `droplet` SMB account (the `samba` service's `ACCOUNT_droplet`). **Generated by `setup.sh`** (alphanumeric, 20 chars — it gets typed into OS connect dialogs); surfaced to owner/admin via the dashboard's "Connect network drive" dialog. Empty → smbd's `null passwords = no` default refuses every logon (fails closed) and the API returns `password: null` |
| `SAMBA_MEM_LIMIT` / `SAMBA_CPUS` | `samba` container resource ceilings (ADR-021; defaults `256m` / `1.0`) |
| `FILES_API_URL` | Files-API target for the MCP file tools (default `http://orchestrator:3000/api/files`). Despite the client's historical "nextcloud" name, raw Nextcloud can't serve these tools (WARP-861) |
| `WEB_FETCH_URL` | Orchestrator → `web-fetch` service target for the ambient-data tools (`get_weather`/`currency_convert`; default `http://web-fetch:8010`). The service is `web`-profile-gated AND behind the `ambient_data` off-LAN channel — both default off (WARP-1436) |
| `WEB_FETCH_SERVICE_TOKEN` | Bearer secret shared by the orchestrator and the `web-fetch` service (per-device, generated into `.env`, never tracked). Unset → web-fetch refuses all requests and the orchestrator's `/api/web/*` routes fail closed (WARP-1436) |
| `ERP_SQL_BRIDGE_URL` | Orchestrator → `erp-sql-bridge` target for the direct-SQL Eaglesoft track (WARP-1106). **Default EMPTY, deliberately**: the bridge is only useful once an operator has vendored the license-gated SAP SQL Anywhere client into its image (`services/erp-sql-bridge/vendor/README.md`), so an empty value leaves the connector blocked with the accurate "needs the SAP client" remediation instead of reporting a connection failure nobody can act on. Set to `http://erp-sql-bridge:9095` once the `erp` profile is on. The REST track (`eaglesoft-api`) ignores it |
| `ERP_DB_HOST` / `ERP_DB_PORT` | The practice's SQL Anywhere server, read by the **bridge** (defaults: unset / `2638`). Unset → `/health` reports `NOT_CONFIGURED` rather than trying localhost |
| `ERP_DB_NAME` / `ERP_DB_SERVER_NAME` | Database and server name on that box (both default `PattersonPM`) |
| `ERP_DB_RO_USER` / `ERP_DB_RO_PASSWORD` | The practice's **read-only** database account (default user `droplet_ro`; provisioned by `services/erp-connector/sql/provision.sql` with SELECT and nothing else). Read from the bridge's own environment and chosen by ROUTE — a caller can never name an identity. Unset password → reads report `NOT_CONFIGURED` |
| `ERP_DB_RW_USER` / `ERP_DB_RW_PASSWORD` | The **write** account (default user `droplet_rw`), created unusable and granted only the one enabled write capability. Unset is the normal state: writes are opt-in, and a missing password is a config error rather than a silent fallback to the read account |
| `ERP_ODBC_DRIVER` | unixODBC driver name the bridge connects with (default `SQL Anywhere 17`). Selecting a driver whose name contains `postgres` switches the connection string to psqlODBC's keyword vocabulary — that is how `scripts/test-erp-sql-bridge.sh` drives the service against a real database without the SAP binaries |
| `ERP_DB_ENCRYPTION` | SQL Anywhere `Encryption=` value (default `NONE`, the documented LAN default). Set to `TLS` where the practice's server has server-side TLS configured |
| `ERP_DB_POOL_MAX` / `ERP_DB_TIMEOUT_S` | Bridge connection-pool ceiling per (identity, target) and connect timeout in seconds (defaults `4` / `10`) |
| `ERP_SQL_BRIDGE_MEM_LIMIT` / `ERP_SQL_BRIDGE_CPUS` | `erp-sql-bridge` container resource ceilings (ADR-021; defaults `256m` / `0.5`) |
| `ERP_EXPORT_DROP_ROOT` | Container path the **export-drop** track reads a practice's own exported reports from (WARP-1964; providers `<vendor>-export`). **Default EMPTY, deliberately** — the compose mount can exist while the track stays off, the same opt-in-twice shape as `ERP_SQL_BRIDGE_URL`. Set to `/data/erp-exports` to enable. This is operator config and is **never** taken from a request body: a caller-supplied path here would be an arbitrary-file read inside the orchestrator. Read by `apps/orchestrator/src/services/erp-provider.ts` |
| `ERP_EXPORT_DROP_HOST_PATH` | The **host** path compose bind-mounts read-only at `/data/erp-exports` (default `../data/erp-exports`). On an appliance point it at the CIFS mount of the practice's export share. The `:ro` is load-bearing, not decorative — it is what makes "Droplet cannot alter the practice's data" a property of the deployment rather than a promise about our code |
| `ERP_EXPORT_DROP_PROFILES` | Path to a JSON file of operator-authored export profiles (header signature → canonical columns). Maps a practice-management system we ship no built-in profile for, or corrects a built-in whose columns do not match that site's report layout, with no release. ## FIPS 140-3 policy

FIPS is a **per-customer option, default OFF** (WARP-318). The full operator +
auditor guide is [`docs/fips.md`](fips.md); the essentials:

- **Single knob.** `DROPLET_FIPS_MODE` (`0`/`1`) is the only thing an operator
  sets. Everything else (`OPENSSL_CONF`, `DROPLET_FIPS_REQUIRED`,
  `NODE_OPTIONS`, and — since WARP-233 — `PG_SSLMODE`,
  `PG_HBA` plus the `sslmode` param of `DATABASE_URL`) is **derived** by
  `setup.sh` — do not hand-edit those, and never add `OPENSSL_MODULES`
  (removed by WARP-1063: a process-wide module path breaks multi-libcrypto
  processes; see `docs/fips.md`). The flag is an **explicit boolean**,
  never inferred from ambient state (mirrors `DOCS_ENABLED` /
  `SINGLE_BOX_MODE`).
- **Default posture is unchanged.** With `DROPLET_FIPS_MODE=0` (the default) the
  rendered stack is byte-identical to a non-FIPS install: modern crypto,
  TLS 1.3, OpenSSL defaults, `crypto.getFips()===0`, MD5 available.
- **No rebuild to flip.** Every image already ships the NIST-validated OpenSSL
  FIPS provider (CMVP #4282, WARP-967) **dormant**. `setup.sh --fips` (or
  `--no-fips`) only rewrites `.env`; on an existing box:
  `setup.sh --fips --skip-docker --skip-build --skip-drivers` then restart.
- **FIPS restricts, it does not add strength.** Turning it on narrows crypto to
  FIPS-approved algorithms for certification; it does not make the system
  "more secure" in the informal sense.
- **Postgres + FIPS — two stacked issues.** (1) **WARP-233 decision (A),
  implemented, scoped to the knob.** Default posture is TLS 1.3 + SCRAM only
  (`hostssl`-only `docker/postgres/pg_hba.conf`, every `DATABASE_URL` pins
  `sslmode=require`); `setup.sh --fips` flips the intra-compose DB hop to
  plaintext+SCRAM on the private container bridge (`PG_SSLMODE=disable`,
  `PG_HBA=pg_hba.fips.conf`, `DATABASE_URL` `sslmode` rewritten), and `--no-fips`
  restores TLS-only. App-layer PHI/PII column encryption applies in both
  postures; decision (A) sign-off is tracked on the WARP-233 PR. (2)
  **Separately, the WARP-317-surfaced FIPS boot block is FIXED (WARP-1063).**
  The `P1011` / `LIBRARY_HAS_NO_CIPHERS` crashes were the validated provider
  failing to activate in the second libcrypto instance of multi-OpenSSL
  processes (Node + Prisma, pyca cryptography + system libssl — the FIPS
  module cannot be initialized twice from one file, openssl#25553). Each image
  now ships a per-runtime `fips.so` copy, `OPENSSL_MODULES` is gone from the
  derived env, and the boot self-tests positively probe an approved digest, so
  FIPS-on boots end-to-end (asserted by WARP-317's full-stack smoke test). See
  [`docs/fips.md`](fips.md).
- **Dev opt-out.** `DROPLET_FIPS_MODE=0` (default). The boot self-test skips
  silently when `DROPLET_FIPS_REQUIRED` is unset/false.
