# Launch-blocker fix plans (ADR-style)

_Generated 2026-05-30 by a 20-agent /architecture workflow. Each plan: root cause, options w/ trade-offs, chosen fix, steps, acceptance, tests, risks. Keyed to the WARP ticket carrying it._


## WARP-559 — Guard the managed-switch control API with requireScope at the mount point

**Area:** auth · **Severity:** critical · **Effort:** S


**Root cause.** WARP-503 was scoped to add RBAC mount guards to the network, routing, and switch control surfaces, but the switch surface was only partially completed. The switch router was authored (apps/orchestrator/src/routes/switch.ts) and its in-handler safety layer (evalSwitchCommand to evaluateNetworkCommand) was wired, but the actual authorization guard at the mount in apps/orchestrator/src/app.ts:165 (app.use("/api", createSwitchRouter(prisma))) was never added — it mounts bare, with no requireScope wrapper. The mistake is that evalSwitchCommand LOOKS like a gate: it performs confirmation, safety tiers, and audit. But it evaluates command safety/intent, not caller identity or scope, and it explicitly tolerates req.user?.id being undefined (passed through on every mutating route at switch.ts lines 227, 245, 249, 267, 285, 302, 320, 335, 348, 362). So an unauthenticated/guest-tier session that satisfies confirmation can reach disablePort, disablePortPoe, and VLAN mutations.


**Options considered.**
- *requireScope guard at the switch mount in app.ts (match sibling pattern)* — **chosen**. Pros: Matches the network/routing/cameras/vpn convention already in app.ts; wraps the whole router so no route can be forgotten (the exact failure mode here); reuses tested middleware; tiny diff; closes all 10 mutating routes at once. Cons: The switch router mixes read GETs and write routes under one /api mount, so a single write-scope on the mount would also block read-only viewers from status; requires a read/write split or a path-scoped sub-mount to preserve read access (still a small, well-understood change).
- *Per-route requireScope inside switch.ts on each mutating handler* — **rejected**. Pros: Naturally separates read GETs from write routes; allows finer per-operation scopes (PoE vs VLAN); co-locates guard with handler. Cons: ~10 routes to annotate means 10 chances to miss one (precisely how this bug happened); diverges from the codebase's mount-level convention; larger review surface for a launch-blocker; higher regression risk if a future route is added without the annotation.
- *Harden evalSwitchCommand to reject undefined req.user / enforce identity* — **rejected**. Pros: No app.ts change; single chokepoint already called by every mutating route. Cons: Conflates authorization with safety/confirmation/audit (two distinct concerns); evalSwitchCommand is per-command not per-mount and currently tolerates anonymous callers by design; would require rewriting its contract and the network-safety service it delegates to; diverges from how the rest of the codebase authorizes; an under-engineered band-aid that masks the missing mount guard rather than restoring the WARP-503 invariant.

**Recommended fix.** Wrap the switch mount with a requireScope(...) guard in apps/orchestrator/src/app.ts:165, matching the exact pattern the network/routing/cameras/vpn sibling mounts already use. This is the smallest, most proven, lowest-blast-radius fix: it reuses the existing, tested authorization middleware and wraps the whole router so no individual route can be missed (which is exactly how this bug arose). Note the switch router carries both read routes (GET /switch/ports, /vlans, /poe, /system) and mutating routes under the same /switch prefix, all mounted at "/api"; to avoid locking legitimate read-only viewers out of status while still gating mutations, either (a) move the requireScope guard to a path-scoped sub-mount covering only the mutating verbs, or (b) split the router into a read mount (read scope) and a write mount (write scope), mirroring how the network routes separate read vs write scopes. Use the same scope identifier the routing/network write mounts use for hardware control (confirm the exact scope name against the requireScope definition and the scope enum; introduce a dedicated switch:write scope only if switch control should be independently grantable, otherwise reuse the network-control write scope to stay consistent with WARP-503's grouping). Leave evalSwitchCommand unchanged — it remains the correct safety/confirmation/audit layer that runs after authorization.

**Implementation steps.**
1. Read the requireScope middleware definition and the scope/role enum it validates against (search apps/orchestrator/src/middleware and src/routes for requireScope usage, e.g. how createNetworkRouter / createRoutingRouter / createVpnRouter are guarded). Confirm the exact call signature and the canonical write scope used for network/router hardware control.
2. Decide the scope: reuse the existing network-control write scope (consistent with WARP-503 grouping network+routing+switch) OR add a dedicated switch:write. If adding one, register it in the scope enum/constants and in the role-to-scope mapping so existing admin/operator roles receive it and guest/viewer do NOT.
3. Resolve the read-vs-write split: the switch router serves both GET status routes and mutating routes under the same /switch prefix. Either split createSwitchRouter into a read router (read scope) and a write router (write scope) mounted separately in app.ts, or apply requireScope as path-scoped middleware matching only the mutating verbs/paths. Mirror whatever pattern the network routes already use for read vs write separation.
4. Edit apps/orchestrator/src/app.ts:165 to apply the requireScope guard to the switch mount per the chosen split (e.g. app.use('/api', requireScope(writeScope), createSwitchWriteRouter(prisma)) alongside a read-scoped read mount), matching the sibling mounts on adjacent lines.
5. Leave apps/orchestrator/src/routes/switch.ts handler bodies and evalSwitchCommand semantics unchanged; confirm evalSwitchCommand still runs after the new guard (it is invoked inside the handlers, so authorization now precedes safety/confirmation/audit).
6. Add a regression test (see testStrategy) asserting a guest/no-scope session gets 403 on every mutating switch route and that an authorized session passes the guard while read-only viewers can still GET status.
7. Run npm run test:orchestrator and scripts/test-security.sh to confirm no scope regressions.
8. Reference WARP-503 in the commit/PR (e.g. 'fix(switch): add requireScope guard to /switch mount - closes the gap WARP-503 missed') so the closed ticket's omission is traceable.

**Acceptance criteria.**
- The switch mount in apps/orchestrator/src/app.ts:165 applies a requireScope(...) guard using the same scope convention as the network/routing/vpn sibling mounts.
- No mutating route in apps/orchestrator/src/routes/switch.ts (port enable/disable, VLAN create/delete/membership, PoE enable/disable, WAN detect, camera setup, command/confirm) is reachable without passing the scope check.
- A session lacking the required scope (guest/viewer or no scope) receives HTTP 403 from every switch mutation route, verified by an automated test that loops over all mutating routes.
- A session WITH the required scope still reaches the handler and evalSwitchCommand still runs (no behavioral change for authorized callers).
- Read-only viewers retain access to GET /switch status routes if a read/write split is used (no over-restriction regression).
- evalSwitchCommand is unchanged; authorization and safety/confirmation/audit remain separate layers.
- Every hardware-control mount in app.ts (cameras, matter, smart-home, network, routing, switch, files, storage, vpn) now has a requireScope guard; the WARP-503 invariant holds with no exceptions.
- npm run test:orchestrator and scripts/test-security.sh pass.

**Test strategy.** Add an orchestrator route test alongside the existing WARP-503 network/routing RBAC tests (apps/orchestrator/src/routes/network.*.test.ts are the structural template). Parameterize over EVERY mutating switch route (POST /switch/ports/:port/enable|disable, POST /switch/vlans, DELETE /switch/vlans/:id, POST /switch/vlans/:id/membership, POST /switch/poe/:port/enable|disable, POST /switch/wan/detect, POST /switch/setup/cameras, POST /switch/command/confirm) and assert: (1) a guest/no-scope token returns 403 and the switch.client service is never invoked; (2) a token with the required scope passes the guard and reaches the handler (mock switchClient and the network-safety service to isolate authorization). Looping over the route table means any future unguarded switch route fails CI, catching the regression class that produced this bug. Optionally add a structural assertion in scripts/test-security.sh that every control-surface mount in app.ts is wrapped in requireScope.

**Risks.**
- Wrong scope identifier could over-restrict (lock admin/operator out of switch control) or under-restrict (grant guests). Mitigate by confirming the scope against the live requireScope enum and role-to-scope mapping and testing both an authorized and unauthorized tier.
- A blanket write-scope on the single /switch mount would also block read-only GET status routes; must split read vs write (or path-scope the guard) or viewers lose status visibility.
- If a dedicated switch:write scope is added but not mapped to existing admin/operator roles, authorized users get 403 (functional regression); update role mappings in the same change and assert an authorized session passes.
- POST /switch/command/confirm executes the queued mutation (switch.ts lines 160-213) and must be guarded with the same write scope as the routes that create the confirmation token, or it becomes an unguarded execution bypass.

**Files.** `apps/orchestrator/src/app.ts`, `apps/orchestrator/src/routes/switch.ts`, `apps/orchestrator/src/middleware (requireScope definition + scope/role enum, only if adding a dedicated switch:write scope)`, `apps/orchestrator/src/routes/switch.rbac.test.ts (new, mirror network.*.test.ts)`

## WARP-560 — AI Gateway accepts unauthenticated inbound requests from any LAN host

**Area:** auth · **Severity:** critical · **Effort:** M


**Root cause.** The ai-gateway FastAPI app (services/ai-gateway/main.py) was built as an internal provider router reachable only via the orchestrator, so it only ever installed RateLimitMiddleware and never an inbound authentication check. But nginx proxies the /ai/ location publicly (docker/nginx.conf:84) with no auth_request directive, so the gateway is directly reachable by any client that can hit the host's :80/:443. Meanwhile the sibling switch service already established the correct in-repo pattern (ServiceAuthMiddleware validating a shared service token, services/switch/main.py:66) and the orchestrator gates routes with requireScope mount guards (apps/orchestrator/src/app.ts) — the gateway simply never adopted either. The result is that inference (/ai/chat), session reads (/ai/sessions/*), model listing, and provider-API-key writes (/ai/keys/{provider}) are all exposed with zero authentication, bypassing the orchestrator's RBAC entirely. This is a defense-in-absence gap: auth was assumed at a layer (orchestrator) that the network topology does not actually force traffic through.


**Options considered.**
- *App-level ServiceAuthMiddleware in the gateway (mirror services/switch ServiceAuthMiddleware)* — **chosen**. Pros: Reuses a pattern already proven and reviewed in this repo (services/switch/main.py:66); enforcement lives next to the code being protected so it cannot be bypassed by a future nginx/topology change; testable with FastAPI TestClient in the same suite as RateLimitMiddleware; fail-closed is trivial to implement; no new dependency. Cons: Requires threading a new token through .env, setup.sh, the gateway, and the orchestrator's outbound client; every legitimate caller must now send the header.
- *nginx auth_request → orchestrator validation endpoint for /ai/* — **fallback**. Pros: Centralizes auth at the edge; consistent with how a future unified gateway-auth story might look; no per-service code. Cons: Does not protect the gateway if reached by any path other than this nginx vhost (compose network, host port, future ingress) — enforcement is not co-located with the asset; adds a round-trip to the orchestrator on every inference call; more moving parts to get right than a header check; the repo has no existing auth_request precedent to copy, so it is the less-boring option.
- *Bind ai-gateway to localhost-only / drop the nginx /ai/ location* — **rejected**. Pros: Smallest possible change; removes external reachability outright. Cons: Breaks legitimate off-host/MCP and dashboard call paths that rely on /ai/ being proxied; masks rather than fixes the missing-auth root cause (the service is still unauthenticated for anything on the compose network or host); not a real authn solution.

**Recommended fix.** Add a ServiceAuthMiddleware to the ai-gateway that mirrors the one already proven in services/switch/main.py: require a shared service token on every inbound request (Authorization: Bearer <token> or X-Service-Token header), reject with 401 when missing/wrong, and exempt only the unauthenticated liveness path (/health and the gRPC port, which is internal-only on the compose network). The orchestrator becomes the sole legitimate caller and is updated to send the token on its outbound ai-gateway calls. Wire the token through .env (DROPLET_AI_GATEWAY_TOKEN, generated by scripts/setup.sh exactly like the switch/PM service tokens) and fail-CLOSED: if the token env var is empty, the gateway refuses all authenticated routes (503) rather than silently allowing everything, matching the engineering-handbook security-rules §1 fail-closed convention already cited in CLAUDE.md for the PM webhook secret. This is the minimal, boring, blast-radius-contained fix: it reuses an existing in-repo pattern verbatim, adds no new framework, and does not require a redesign of nginx auth_request (which is a reasonable optional hardening, captured as a follow-up).

**Implementation steps.**
1. Read services/switch/main.py around line 66 to copy the exact ServiceAuthMiddleware shape (header names accepted, 401 body, exempt-path handling, how it reads its token from env) so the gateway implementation is byte-for-byte consistent with the established pattern.
2. In services/ai-gateway/main.py, add a ServiceAuthMiddleware (Starlette BaseHTTPMiddleware) that: reads the expected token from env (DROPLET_AI_GATEWAY_TOKEN); if the env var is empty, return 503 for all protected routes (fail-closed); exempt the /health liveness path (and any other unauthenticated probe) from the check; accept the token via Authorization: Bearer <token> and/or X-Service-Token; return 401 on missing/mismatched token using constant-time comparison (hmac.compare_digest). Register it with app.add_middleware AFTER (i.e. so it runs before) RateLimitMiddleware so unauthenticated traffic is rejected before consuming rate-limit budget.
3. Confirm the gRPC EmbedText service on :50051 is not exposed by nginx and is compose-internal only; if it is reachable externally, gate it too or document that it stays internal — note this explicitly in the PR description.
4. Update the orchestrator's outbound ai-gateway client (the module that builds requests to AI_GATEWAY_URL — grep apps/orchestrator/src for AI_GATEWAY_URL / ai-gateway client) to attach Authorization: Bearer ${DROPLET_AI_GATEWAY_TOKEN} on every request, reading the token from the orchestrator config (apps/orchestrator/src/config.ts).
5. Add DROPLET_AI_GATEWAY_TOKEN to scripts/setup.sh secret generation (same openssl/rand pattern used for the switch token) so a fresh device gets a unique value, and add it to .env.example with an empty default.
6. Add the new var to scripts/test-security.sh allow-list / checks if that script enforces an env-var inventory, and document DROPLET_AI_GATEWAY_TOKEN in CLAUDE.md's Environment variables table.
7. Optionally (hardening follow-up, not blocking): add auth_request or a static token check on the /ai/ location in docker/nginx.conf:84 so unauthenticated requests are dropped at the edge before reaching the gateway; capture as a separate ticket if not done now.
8. Update README/scripts docs noting that ai-gateway now requires the service token and that editing the token in .env requires --force-recreate of the ai-gateway container (per the CLAUDE.md 'Updating .env on a running stack' note).

**Acceptance criteria.**
- A request to /ai/chat, /ai/sessions/*, /ai/models, or /ai/keys/{provider} with no Authorization/X-Service-Token header returns 401 (verifiable with curl against the running stack).
- A request with a wrong token returns 401; a request with the correct DROPLET_AI_GATEWAY_TOKEN succeeds.
- /health remains reachable with no token (liveness probe unaffected).
- With DROPLET_AI_GATEWAY_TOKEN unset/empty, protected routes return 503 (fail-closed), not 200.
- The orchestrator's normal chat/inference flow still works end-to-end through the dashboard because its outbound client now sends the token.
- Token comparison uses hmac.compare_digest (no early-exit string compare).
- ServiceAuthMiddleware runs before RateLimitMiddleware so unauthenticated requests are rejected before rate-limit accounting.
- scripts/setup.sh generates a unique DROPLET_AI_GATEWAY_TOKEN on a fresh provision and the var is documented in CLAUDE.md.

Mirror the structure of any existing ServiceAuthMiddleware test in services/switch. Optionally extend scripts/test-security.sh to assert nginx does not proxy /ai/ without an auth control if the edge-hardening step is taken. These tests make CI fail if a future change drops the middleware or weakens it to fail-open."

**Risks.**
- Token-rotation/footgun: docker restart does not re-read .env (per CLAUDE.md), so an operator rotating DROPLET_AI_GATEWAY_TOKEN must --force-recreate both ai-gateway and orchestrator or the orchestrator will start sending a token the gateway rejects (500/401 'AI not reachable'). Document this in the PR and scripts/README.

## WARP-561 — BYOK provider keys are device-global and weakly encrypted — scope keys per-user and harden the keystore passphrase

**Area:** auth · **Severity:** high · **Effort:** M


**Root cause.** The ai-gateway BYOK keystore was designed for a single-tenant appliance where one operator owns the box, so the key namespace is keyed only by provider. `keystore.py:71` writes ciphertext to `{provider}.enc` with no caller/user component, and `byok.py:36` `get_api_key(provider)` resolves a key purely by provider name — there is no user dimension anywhere in the read or write path. The moment the gateway serves more than one identity (multi-user dashboard, multi-tenant), this becomes a shared mutable slot: any caller's stored OpenAI/Anthropic key overwrites and is readable by every other caller. This is amplified by the companion finding U-GW-AUTH (the gateway does not authenticate callers at all), which removes even the implicit "only the operator can reach this" boundary. Separately, `keystore.py:23` falls back to a hardcoded passphrase when `DEVICE_SECRET` is unset, so on any misconfigured/unprovisioned device the at-rest encryption is effectively cosmetic — a known constant protects every customer's cloud-provider credentials.


**Options considered.**
- *Per-user filesystem namespace (users/{user_id}/{provider}.enc) + reuse existing service-auth identity + fail-closed secret* — **chosen**. Pros: Minimal blast radius; mirrors patterns already in the repo (ServiceAuthMiddleware, requireScope, fail-closed-on-missing-secret posture); no new dependency; trivially testable; preserves existing single-operator deployments via an owner-id migration shim Cons: Requires U-GW-AUTH (caller identity) to be real before per-user scoping has teeth; filesystem layout migration needs a one-time shim
- *Move BYOK key storage into the orchestrator's Postgres (Prisma) keyed by userId, gateway fetches via the orchestrator* — **rejected**. Pros: Single source of truth for identity; gets transactional guarantees and RBAC for free via the orchestrator; centralizes secrets where auth already lives Cons: Large cross-service refactor; introduces a synchronous orchestrator dependency in the gateway hot path; secrets now traverse an extra hop; far more than this launch-blocker needs
- *Keep device-global keys but lock the endpoint down to operator-only (single shared key, no per-user scoping)* — **rejected**. Pros: Smallest possible change; closes the cross-user overwrite if only one operator is ever authenticated Cons: Band-aid — does not fix the actual finding (keys remain shared mutable state); breaks the moment a second user is provisioned; masks the issue rather than resolving it

**Recommended fix.** Make the BYOK keystore user-scoped and fail-closed on a missing device secret, mirroring the auth patterns already proven elsewhere in this repo. (1) Introduce a caller identity at the gateway by reusing the same shared-secret/identity middleware the orchestrator and switch service already use (`ServiceAuthMiddleware` in `services/switch/main.py`, `requireScope` mount guards in `apps/orchestrator/src/app.ts`); this is the U-GW-AUTH prerequisite and must land first or in lockstep. (2) Thread a `user_id` (the authenticated subject) through `byok.get_api_key(provider, user_id)` and the keystore set/get/delete signatures, and change the on-disk layout from `{provider}.enc` to a per-user namespace `users/{user_id}/{provider}.enc` (sanitized) so one user can never read or clobber another's key. (3) Remove the hardcoded passphrase fallback at `keystore.py:23` — when `DEVICE_SECRET` is absent the keystore must refuse to encrypt/decrypt and raise at startup, matching the fail-closed-on-missing-secret posture mandated in CLAUDE.md. Keep the migration boring: a one-time shim that, on first read of a legacy unscoped `{provider}.enc`, treats it as belonging to a configurable single "owner" user_id so existing single-operator deployments don't lose their keys. This is the minimal, proven-pattern fix: no new framework, just a user dimension in the key path plus a fail-closed secret check.

**Implementation steps.**
1. Confirm/land U-GW-AUTH first: add caller authentication + identity extraction at the ai-gateway, copying ServiceAuthMiddleware from services/switch/main.py so every request carries an authenticated user_id (subject). This is the precondition; per-user scoping is meaningless without it.
2. services/ai-gateway/auth/keystore.py:23 — remove the hardcoded passphrase fallback. Read DEVICE_SECRET once at module/keystore init; if unset or empty, raise a startup-time error (RuntimeError) so the service fails closed instead of encrypting with a known constant. Match the fail-CLOSED-on-missing-secret posture documented in CLAUDE.md.
3. services/ai-gateway/auth/keystore.py:71 — change the on-disk path from '{provider}.enc' to a per-user namespace: 'users/{sanitized_user_id}/{provider}.enc'. Add a _user_dir(user_id) helper that validates/sanitizes user_id (reject path separators, '..', empty) to prevent path traversal. Apply the same path change to the corresponding get/delete code paths in this file.
4. services/ai-gateway/auth/keystore.py — update set_api_key/get_api_key/delete signatures to require user_id as a mandatory first argument; no default that resolves to a global slot.
5. services/ai-gateway/auth/byok.py:36 — change get_api_key(provider) to get_api_key(user_id, provider) and pass the authenticated subject from the request context through to the keystore. Update every caller in the gateway request path.
6. Add a one-time migration shim: on read, if a legacy unscoped '{provider}.enc' exists and no per-user file is present, treat it as owned by a configurable BYOK_OWNER_USER_ID (defaulting to the provisioned operator) and copy/move it into users/{owner}/{provider}.enc. Log the migration once. This preserves existing single-operator deployments.
7. Add the user_id dimension to any BYOK HTTP route handlers (set/get/delete key) so they derive user_id from the authenticated request, never from a client-supplied field.
8. Update services/ai-gateway documentation / .env notes and CLAUDE.md's environment table to record that DEVICE_SECRET is now mandatory for BYOK (no fallback) and that keys are per-user.
9. Add unit + integration tests (see test strategy) and wire them into npm run test:ai-gateway.

**Acceptance criteria.**
- get_api_key and the keystore set/get/delete require a user_id argument; there is no code path that reads or writes a key without one.
- Keys are stored at users/{user_id}/{provider}.enc; two different user_ids storing the same provider produce two distinct files and cannot read each other's key.
- User A's stored OpenAI/Anthropic key is never returned to, nor overwritten by, a request authenticated as User B (covered by a test).
- With DEVICE_SECRET unset, the ai-gateway fails to start (or the keystore refuses operations) with a clear error — it never encrypts with a hardcoded constant. grep for the old hardcoded passphrase returns nothing.
- user_id values containing path separators or '..' are rejected before touching the filesystem (path-traversal test passes).
- An existing single-operator deployment with a legacy {provider}.enc still resolves its key after upgrade via the owner-id migration shim.
- BYOK route handlers derive user_id from the authenticated request context, never from a client-supplied request field.
- npm run test:ai-gateway passes including the new cross-user isolation and fail-closed tests.

**Test strategy.** "Add pytest cases under services/ai-gateway tests: (1) cross-user isolation — store a key as user 'alice', assert user 'bob' get_api_key returns None and that bob storing the same provider does not mutate alice's file; (2) fail-closed — instantiate the keystore with DEVICE_SECRET unset and assert it raises rather than using a fallback passphrase; (3) path-traversal — assert user_id values like '../../etc' or with slashes are rejected; (4) round-trip per user — set/get/delete scoped to a user_id; (5) legacy migration — seed a legacy {provider}.enc, assert it is readable by the configured owner user_id after upgrade and not by others. Add one integration test through the BYOK route(s) proving the user_id comes from the authenticated subject, not the request body. Wire all into the existing npm run test:ai-gateway target so CI catches regressions."

**Risks.**
- Per-user scoping only delivers security once U-GW-AUTH (caller authentication/identity) is real; if that lands incompletely, user_id could be spoofable and the scoping becomes decorative. Sequence them together.
- Removing the DEVICE_SECRET fallback will hard-fail any currently-running deployment that never set it — must be called out in release notes and verified that setup.sh always provisions DEVICE_SECRET.
- The legacy {provider}.enc → owner-namespace migration must run idempotently; a botched migration could orphan an operator's existing cloud keys (mitigated by copy-then-verify rather than move, and by the migration unit test).
- Changing keystore/byok signatures is a breaking change for every internal caller; missing one leaves a code path that still reads the global slot — grep for all call sites before merge.
- user_id used as a filesystem path component is an injection surface; sanitization must be strict (allowlist, not blocklist).

**Files.** `services/ai-gateway/auth/keystore.py`, `services/ai-gateway/auth/byok.py`, `services/ai-gateway/main.py`, `services/ai-gateway/.env or .env.example`, `CLAUDE.md`

## WARP-562 — Orchestrator CORS reflects any origin with credentials — restrict to an allowlist

**Area:** auth · **Severity:** high · **Effort:** S


**Root cause.** apps/orchestrator/src/app.ts:75 configures the cors middleware as `cors({ credentials: true, origin: true })`. `origin: true` makes the cors package echo back whatever Origin header the request carries, and combined with `credentials: true` it emits `Access-Control-Allow-Origin: <attacker-site>` plus `Access-Control-Allow-Credentials: true`. Because sessions are cookie-based (`droplet_session`, SameSite=lax), the cookie still rides top-level navigations and simple cross-site GETs, so any website the appliance owner visits can perform credentialed cross-origin reads against the local API and read the response. This is the quickstart-default mistake: no explicit origin policy was ever supplied. The sibling ai-gateway already learned this lesson (services/ai-gateway/main.py:121-128 refuses CORS_ORIGINS=* when credentials are enabled); the orchestrator simply never got the equivalent guard.


**Options considered.**
- *Env-driven exact-match allowlist via cors origin callback (credentials kept)* — **chosen**. Pros: Framework-native (cors supports a function origin); never reflects untrusted origins; matches ai-gateway's existing CORS_ORIGINS guard; configurable per-deployment via .env; keeps cookie auth working for the real dashboard origin; fail-fast on wildcard+credentials. Cons: Operators must declare their dashboard origin, mitigated by the https://droplet-ai.local default the cert SANs already cover.
- *Drop credentials (origin: true, credentials: false)* — **rejected**. Pros: One-character change; browser won't expose cookies cross-site. Cons: Breaks the legitimate cross-origin case if dashboard and API ever differ in origin; masks intent rather than declaring policy; a future dev re-enabling credentials silently reintroduces the hole; under-engineered band-aid.
- *Remove cors middleware, rely on same-origin behind Nginx* — **fallback**. Pros: In prod everything sits behind the single Nginx host so same-origin holds and no CORS headers are needed; smallest surface. Cons: Breaks local dev (Next.js :3000 vs orchestrator port) and any native/mobile pairing client that needs CORS; forces a dev-only conditional that is just a worse allowlist.

**Recommended fix.** Replace `origin: true` with an explicit, env-driven allowlist evaluated by a callback, keeping `credentials: true`. ## WARP-563 — MCP server: make tool-call trust explicit instead of inferring full privilege from absent claims

**Area:** auth · **Severity:** high · **Effort:** S


**Root cause.** The MCP server decides whether a caller may invoke write/privileged tools by inferring trust from the absence of a claims object: `const trustedPrincipal = claims === undefined` (services/mcp-server/src/server.ts:30), which is then passed into both `filterToolsForRole(...)` (line 37) and `canCallTool(...)` (line 60). The problem is not CLAUDE.md's "No guessing, ever" rule (that rule is about persistent state columns, not transport trust); it is that the stdio-trusted / HTTP-untrusted split has **no type-level enforcement** — full privilege is derived from a missing field rather than declared explicitly. It is correct today only because of an unwritten invariant — the stdio transport (the in-process orchestrator child, wired in src/index.ts:283 with no claims) is the sole path that passes undefined, while the HTTP transport always synthesizes a verified-JWT Claims object (src/transports/http.ts:100-114). That invariant lives in a code comment and a developer's head, not in the type system. Any future transport, refactor, test harness, or error path that reaches `createServer(deps)` without claims silently inherits full write privilege — a network-path RBAC bypass that is one edit away.


**Options considered.**
- *Explicit TrustContext discriminated union required per createServer call; gate fails closed when unspecified (chosen)* — **chosen**. Pros: Removes state-by-absence entirely; trust becomes a declared, typed input every transport must supply. Reuses existing rbac.ts helpers (filterToolsForRole/canCallTool) unchanged. Matches repo patterns: WRITE_TOOLS derived from requiresWrite, requireScope mount guards, fail-closed ServiceAuthMiddleware. TS discriminated union makes a forgotten posture a compile error, not a silent grant. Small blast radius: createServer signature + two index.ts call sites + http.ts factory type. Cons: Touches the public createServer signature, so stdio bootstrap, the HTTP buildServer factory type, and any tests calling createServer must update in the same commit; modest churn across __tests__ (server-rbac.test.ts, server.test.ts, http/stdio roundtrip).

Cons: Still encodes trust as a loose boolean rather than a named posture; a future caller can pass `true` by copy-paste habit. Weaker compile-time guarantee than a discriminated union and less self-documenting. Leaves the 'one bool away from bypass' shape, only inverted.

Pros: Single code path — every caller is 'authenticated', createServer only ever reads claims.role, deletes the trustedPrincipal concept entirely. Conceptually uniform. Cons: Manufactures a fake owner principal and threads it through RBAC, blurring the real distinction between an in-process trusted child and a network caller; also breaks the WARP-437 `_enhancement` gate at server.ts:108 which is deliberately trusted-stdio-only and must NOT be reachable by any claims-bearing HTTP request. The stdio bootstrap (src/index.ts:283) explicitly constructs `{ kind: 'local-trusted' }`; the HTTP buildServer factory (src/index.ts:303, src/transports/http.ts:114) constructs `{ kind: 'authenticated', claims }`. Inside createServer, derive `trustedPrincipal = trust.kind === 'local-trusted'` and `role = trust.kind === 'authenticated' ? trust.claims.role : undefined`, then keep feeding the existing `filterToolsForRole` / `canCallTool` calls unchanged. Trust can no longer be true by default: an unrecognized/missing posture yields `trustedPrincipal === false` and undefined role, so the existing read-only fallback in rbac.ts denies write tools — fail closed, matching the switch service's `ServiceAuthMiddleware` (services/switch/main.py) and the fail-CLOSED-on-missing-secret rule in CLAUDE.md. Retry makes the lost race a transparent success rather than a 500. ## WARP-564 — Make pairing-code claim atomic to prevent double redemption of single-use codes

**Area:** data · **Severity:** high · **Effort:** S


**Root cause.** The claim handler in apps/orchestrator/src/routes/device-clients.ts (lines 200-309) is a textbook check-then-act TOCTOU race. It reads the code with prisma.pairingCode.findUnique (line 220), branches on the in-memory record.used flag (line 227), then performs a slow ncGenerateAppPassword network round-trip (line 264), and only afterward writes prisma.deviceClient.create (line 274) and prisma.pairingCode.update({used:true}) (line 285) as two independent statements with NO enclosing prisma.$transaction. Because the read-check and the used-flag write are separated by a network call and not serialized, two concurrent claims of the same code both pass record.used===false before either marks it used, so both provision credentials. It is compounded at the data layer: PairingCode.used (schema.prisma line 306) is an ordinary boolean with no conditional-write/uniqueness enforcement, so the DB cannot reject the second redemption. This violates the repo CLAUDE.md "enforce persistent state explicitly, never guess/derive" standard.


**Options considered.**
- *Atomic conditional claim (updateMany WHERE used=false) as the gate, plus $transaction with deviceClient.create and compensating release* — **chosen**. Pros: Single boring SQL UPDATE is the gate; Postgres row lock serializes concurrent claimers so exactly one wins. No new deps, matches existing prisma.$transaction convention. Rollback/compensation releases the code and the orphaned Nextcloud token on failure. Blast radius is one handler. Indexable, explicit-state compliant. Cons: Slightly more code than a naive wrap; must order the slow ncGenerateAppPassword call outside the tx and add a 409 path for the loser.
- *Wrap the existing findUnique-check-create-update sequence in prisma.$transaction unchanged* — **rejected**. Pros: Smallest diff; matches the convention the misleading line-272 comment already claims. Cons: Does NOT fix the race at Prisma/Postgres default READ COMMITTED: a plain SELECT inside a tx does not lock the row, so two transactions both read used=false and both proceed. - *Schema hardening only — add nullable-unique redeemedByDeviceClientId column / constraint plus app retry* — **fallback**. Pros: Defense-in-depth at the DB layer; structurally impossible to double-redeem even from a future code path. Cons: A boolean 'used' cannot be made meaningfully unique; needs a migration and still requires the atomic claim in app code to be correct. Heavier than needed for the launch blocker. Best as follow-up hardening, not the primary fix.

**Recommended fix.** Make the single statement that flips used=false→true the authoritative gate, and only provision credentials if that statement actually claimed the row. Because updateMany emits a single UPDATE ... WHERE used = false, the Postgres row lock serializes concurrent claimers so exactly one wins regardless of timing. Order it so the code is claimed atomically before creating the DeviceClient, and wrap claim + deviceClient.create in a prisma.$transaction so a failure after the claim rolls the used flag back (no code burned without a credential issued). Keep ncGenerateAppPassword OUTSIDE the open transaction window (it is slow and external): claim-then-create in the tx after the app password is in hand, and on any post-claim failure perform a compensating release (used=false) plus best-effort ncDeleteAppPassword so no orphaned Nextcloud credential lingers. This matches the repo's prisma.$transaction convention and the explicit-state standard, adds zero dependencies, and confines blast radius to one handler. Do NOT merely wrap the existing sequence in a transaction at default READ COMMITTED isolation — a plain SELECT does not lock the row, so the race survives; the conditional UPDATE must be the gate.

## WARP-567 — Global Express error handler must honor err.status/err.statusCode instead of hardcoding 500

**Area:** release · **Severity:** high · **Effort:** S


**Root cause.** apps/orchestrator/src/middleware/error-handler.ts:13 unconditionally calls res.status(500) and ignores any status the error carries. The codebase already established the opposite convention: typed errors carry an HTTP status and a JSON body (apps/orchestrator/src/types/device-registry-error.ts:39 `status` + line 128 `toJSON()`; apps/orchestrator/src/types/router-error.ts:31 `status` + line 72 `toJSON()`), and route-local helpers surface them precisely (apps/orchestrator/src/routes/network-error-handler.ts:13 `res.status(err.status ?? 400)`; apps/orchestrator/src/routes/aps.ts:160 `res.status(err.status)`). This divergence drives the U-FAILING-TESTS cases that expect 4xx/200 but observe 500.


**Options considered.**
- *Status-aware global handler reading err.status ?? err.statusCode (+ ZodError->400), localized to error-handler.ts* — **chosen**. Pros: One-file change, zero new deps, mirrors the existing typed-error convention (DeviceRegistryError/RouterError .status + toJSON, network-error-handler.ts line 13). Lets the 249 next(err) call sites and already-typed errors flow through unchanged. Minimal blast radius; preserves correct redaction/logging. Cons: Relies on errors carrying a status (or being a ZodError); untyped throws still default to 500, which is the correct conservative behavior.
- *Adopt the http-errors package and rewrite routes to throw createHttpError(...)* — **rejected**. Pros: Standard error objects with built-in status and an expose flag for redaction. Cons: New dependency for what is fundamentally a one-line guard; invites churn across 249 call sites and two existing bespoke error classes; over-engineered and ignores the project's home-grown typed-error pattern.
- *Add per-route try/catch + res.status everywhere (like network-error-handler) instead of fixing the global handler* — **rejected**. Pros: Explicit per-route control. Cons: Leaves the terminal catch-all still defaulting everything to 500 — masks rather than fixes the root cause; huge surface area; the global handler exists precisely to avoid this duplication.

**Recommended fix.** Make the global handler the single source of truth for status derivation, mirroring the project's existing typed-error contract. Read a numeric status from `err.status ?? err.statusCode`; if absent, map a `ZodError` to 400 (zod is already a dependency and `.parse()` is used in many routes); validate the result is an integer in 400-599 and default to 500 otherwise. Preserve the two behaviors that are already correct: structured pino logging (line 12) and stack/message redaction outside development (line 16). If the error exposes `toJSON()` (DeviceRegistryError/RouterError do), surface that payload under `error` so the body shape matches network-error-handler.ts. Do NOT add a new error framework (e.g. http-errors) and do NOT touch the 249 `next(err)` call sites — the fix is one localized guard that lets the already-typed errors flow through unchanged.

**Implementation steps.**
1. In apps/orchestrator/src/middleware/error-handler.ts, derive the status: `const raw = (err as any)?.status ?? (err as any)?.statusCode;` then if raw is missing and `err?.name === 'ZodError'` use 400; then `const status = Number.isInteger(candidate) && candidate >= 400 && candidate <= 599 ? candidate : 500;`.
2. Branch logging by severity: keep `logger.error({ err }, 'Unhandled error')` for status >= 500; use `logger.warn({ name: err.name, message: err.message, status }, 'Client error')` for 4xx so expected validation failures don't fire error-level alerts and don't pollute 5xx-based alerting.

5. Call `res.status(status).json(body)`, keeping the 4-arg `(err, _req, res, _next)` signature so Express still treats it as the terminal error middleware mounted at app.ts:334.
6. Add apps/orchestrator/src/middleware/error-handler.test.ts next to apps/orchestrator/src/middleware/auth.test.ts (reuse its `res.status`/`res.json` = `vi.fn().mockReturnThis()` mock harness).

**Acceptance criteria.**
- An error forwarded via next(err) with `status` (or `statusCode`) of 400/404/409 produces that exact HTTP status from the global handler, not 500.
- A DeviceRegistryError forwarded directly to the global handler yields its `status` and its `toJSON()` body `{ code, message, status? }`.
- A ZodError with no explicit status yields 400.
- A plain `new Error('boom')` with no status still yields 500.

- A 4xx response includes a caller-actionable message regardless of NODE_ENV.

**Test strategy.** Add apps/orchestrator/src/middleware/error-handler.test.ts (Vitest, matching apps/orchestrator/src/middleware/auth.test.ts which mocks `res.status`/`res.json` as `vi.fn().mockReturnThis()` plus a pino spy). Cover: (1) err.status=404 -> res.status(404); (2) err.statusCode=409 -> 409; (3) DeviceRegistryError -> its status + toJSON body; (4) ZodError -> 400; (5) bare Error -> 500 + redacted body with NODE_ENV unset; (6) NODE_ENV='development' -> 5xx body leaks err.message; (7) 4xx -> body carries message even in prod; (8) invalid status (700, NaN, 200) -> 500; (9) log level: 5xx at error, 4xx at warn. **Risks.**

## WARP-572 — Add process-level unhandledRejection/uncaughtException safety net to the orchestrator entrypoint

**Area:** ops · **Severity:** high · **Effort:** S


**Root cause.** apps/orchestrator/src/index.ts registers only SIGTERM/SIGINT handlers (lines 423-424) and a main().catch() for boot failures (lines 427-430); there is no process.on('unhandledRejection') or process.on('uncaughtException'). The orchestrator is an always-on control plane that fires many background promises that escape the request lifecycle: cron-runtime wraps each tick in `void safeRun(...)` inside setInterval (cron-runtime.service.ts:205-211), reminders-poller does `void tick(prisma)` (reminders-poller.ts:93-94), the streaming flush timer in routes/llm.ts:489 runs on a setInterval, and best-effort MQTT/`void recordActivity(...)` calls fire across services. safeRun catches inside the handler, but any rejection that escapes a timer callback or a non-safeRun `void` promise has no process-level catch. On modern Node the default action for an unhandled rejection is to terminate the process, so one stray throw in a background timer can take down the whole appliance with no diagnostic beyond Node's default stderr dump.


**Recommended fix.** Add two process-level handlers in apps/orchestrator/src/index.ts, co-located with the existing SIGTERM/SIGINT registrations, reusing the same pino `logger` and the existing `shutdown` helper. Treat unhandledRejection as logged-but-survivable: log at error with a stable `code: 'unhandledRejection'` field and the rejection reason, and do NOT exit, so a single stray background throw degrades rather than kills the control plane. Treat uncaughtException as fatal-after-flush: log it (pino `logger.fatal`, matching the existing boot-failure handler at index.ts:428), attempt the existing graceful `shutdown()` (cron stop, MCP child stop, prisma.$disconnect), then exit non-zero so Docker's restart policy brings a clean instance back. This matches the codebase's conventions: process lifecycle is already centralized in index.ts, errors are always logged structurally and never silently swallowed (cron-runtime safeRun logging at cron-runtime.service.ts:191-199; naked-error-propagation comments at index.ts:340-345), and the boot path already uses logger.fatal + process.exit(1).

**Implementation steps.**
1. Refactor `shutdown` in apps/orchestrator/src/index.ts (lines 400-421) to accept an exit code, e.g. `const shutdown = async (exitCode = 0) => { ... process.exit(exitCode); }`. Default 0 preserves current SIGTERM/SIGINT behavior; update the two registrations to `process.on('SIGTERM', () => void shutdown(0))` / `('SIGINT', () => void shutdown(0))`.
2. Immediately after the SIGINT registration (currently index.ts:424), add: `process.on('unhandledRejection', (reason) => { logger.error({ err: reason, code: 'unhandledRejection' }, 'Unhandled promise rejection (surviving)'); });`
3. Directly below it add: `process.on('uncaughtException', (err) => { logger.fatal({ err, code: 'uncaughtException' }, 'Uncaught exception, shutting down'); void shutdown(1); });`
4. To make this unit-testable without booting the full stack, extract the handler wiring into a small exported helper in the same file, e.g. `export function registerProcessSafetyNet(log: pino.Logger, onFatal: () => void) { ... }` and call it from main() with `(logger, () => void shutdown(1))`. Keep it in index.ts so process lifecycle stays centralized.
5. Add a vitest test at apps/orchestrator/src/__tests__/process-safety-net.test.ts (repo uses `vitest run` per package.json:9; tests live in src/__tests__/) covering the helper.
6. Run `npm run test:orchestrator` and `npm run build` (tsc) to confirm types and tests pass.

- An uncaughtException produces a pino fatal log containing code:'uncaughtException', invokes the existing shutdown() (cron stop + MCP stop + prisma.$disconnect), then exits with code 1
- Existing SIGTERM/SIGINT graceful shutdown still exits with code 0 (shutdown's exitCode param defaults to 0)
- npm run test:orchestrator and npm run build both pass

**Test strategy.** Add a vitest unit test (apps/orchestrator/src/__tests__/process-safety-net.test.ts) targeting the exported registerProcessSafetyNet(logger, onFatal) helper so no real process boot or process.exit is needed. ## WARP-573 — Guard Prisma migrate-on-boot with an advisory lock + pre-migration snapshot/auto-recovery

**Area:** ops · **Severity:** critical · **Effort:** M


**Root cause.** The orchestrator container's CMD (apps/orchestrator/Dockerfile:153) chains `npx prisma migrate deploy && node dist/index.js` and runs it on every start with zero protection. Two failure modes follow. First, no concurrency guard: any time more than one orchestrator process touches the same Postgres `db` (a `--force-recreate`, an overlapping restart during OTA, or future scale-out), migrations race the `_prisma_migrations` table. Second, and the launch-blocker, no atomicity or recovery around the apply: a Droplet is a single-box appliance with real power-cut risk. `migrate deploy` writes a tracking row before/while applying, so if power is lost mid-migration the table is left with a row where finished_at/rolled_back_at are NULL (a failed migration). Prisma's deploy then refuses to proceed until a human runs `prisma migrate resolve`; the `&&` short-circuits so `node dist/index.js` never runs; Docker's restart policy re-runs the same failing command forever. The device silently bricks into a restart loop only diagnosable by docker-exec into the DB.


**Options considered.**
- *Entrypoint script: advisory lock + pre-migration snapshot + auto-recovery (chosen)* — **chosen**. Pros: Addresses BOTH cited failure modes (no lock, no snapshot) with boring Postgres-native primitives and a shell guard at the boundary, matching repo conventions. Breaks the silent restart loop by auto-recovering or failing loudly. Keeps migration concerns out of app code so a half-migrated schema never boots. Cons: Adds pg client tools to the image and some boot latency/disk for snapshots; recovery branch needs careful, well-tested logic.
- *Advisory lock only (no snapshot; rely on operator `prisma migrate resolve`)* — **rejected**. Pros: Smallest change; fixes the concurrency race; trivial to bolt onto the existing CMD. Cons: Does NOT fix the launch-blocker: a power cut mid-migration still leaves a failed row that bricks every subsequent boot and still needs a human docker-exec. Under-engineered, leaves the actual brick path open.
- *Move migration into application startup with a JS-level lock/transaction inside dist/index.js* — **rejected**. Pros: Single language; can reuse Prisma $transaction patterns already in the codebase; no extra shell script. Cons: Couples app boot to migration in-process, makes pg_dump/restore awkward from Node, and risks the app partially initializing around schema changes. Heavier and cleverer where a boring boundary guard is preferred; harder to reason about under power-cut.

**Recommended fix.** Replace the inline CMD with a dedicated, idempotent entrypoint script (apps/orchestrator/scripts/migrate-and-start.sh) that, before starting the app: (1) acquires a Postgres session-level advisory lock via pg_advisory_lock(<constant>) so only one process migrates at a time and others wait instead of race; (2) takes a pg_dump snapshot of the orchestrator DB to a mounted volume immediately before applying; (3) runs `prisma migrate deploy`; (4) if it detects a previously-failed migration row, restores the snapshot and only then marks that migration `--rolled-back` and retries deploy once (never blind `--applied`, which would lie about state); (5) on unrecoverable failure, logs a loud greppable banner naming the snapshot path and exact remediation command and exits non-zero so the failure is visible in `docker logs` rather than an opaque restart loop. This matches repo conventions: the explicit-state / no-guessing rule (we read the real _prisma_migrations row, never infer), boring shell-level boundary guards (like setup.sh idempotency and requireScope/ServiceAuth mount guards), and Postgres-native primitives (advisory locks) instead of a new framework. Keeps migration concerns out of app code so a half-migrated schema never boots Express.

**Implementation steps.**
1. Create apps/orchestrator/scripts/migrate-and-start.sh (chmod +x, `set -euo pipefail`). Parse/pass DATABASE_URL (pg client tools accept the connection URI directly). Define a fixed constant MIGRATION_LOCK_KEY (e.g. 4815162342) used by all callers.
2. In the script, hold a session-level advisory lock for the whole migration phase: run psql in one invocation that does SELECT pg_advisory_lock(4815162342) -> migrate -> unlock (or hold it via a single long-lived psql session). Document why session-level: it auto-releases if the backend dies, so a power cut while holding it cannot permanently wedge future boots.
3. Before applying, run `pg_dump --format=custom --file=/data/migration-snapshots/pre-migrate-$(date +%s).dump "$DATABASE_URL"` to a mounted volume; prune to the last N (e.g. 3). Skip the snapshot when deploy reports no pending migrations (the common idempotent-restart case) to bound latency/disk.
4. Detect a prior failed migration before deploy: `SELECT migration_name FROM _prisma_migrations WHERE finished_at IS NULL AND rolled_back_at IS NULL ORDER BY started_at DESC LIMIT 1;`. If a row exists, log the recovery banner, restore the latest snapshot with `pg_restore --clean --if-exists`, run `npx prisma migrate resolve --rolled-back <migration_name>`, then continue. This is the auto-recovery path that breaks the silent loop.
5. Run `npx prisma migrate deploy`. On a non-recoverable non-zero exit, print a loud stderr banner (snapshot path + exact `docker exec ... prisma migrate resolve` command) and `exit 1`. Do not fall through to starting the app on a half-migrated schema.
6. After successful deploy, release the advisory lock and `exec node dist/index.js` (exec to preserve PID 1 / signal semantics).
7. Edit apps/orchestrator/Dockerfile: install postgresql-client pinned to major 16 (matching the `db` service) in the run stage, COPY the script in, and change line 153 CMD from `sh -c 'npx prisma migrate deploy && node dist/index.js'` to invoke ./scripts/migrate-and-start.sh.
8. Add a snapshot volume mount (named volume at /data/migration-snapshots) to the orchestrator service in docker/docker-compose.yml.
9. Ensure scripts/factory-reset.sh wipes the snapshot volume so a reset truly returns to out-of-the-box state.
10. Update scripts/README.md and orchestrator docs to describe the new boot sequence, snapshot location, and manual recovery command.
11. Add a CI test (see test strategy) covering the failed-migration recovery and the lock behavior against a throwaway Postgres, wired into test:orchestrator.

**Risks.**

## WARP-577 — Setup-detection must fail CLOSED, not into the first-run wizard, on transient orchestrator errors

**Area:** frontend · **Severity:** high · **Effort:** S


**Root cause.** checkSetupRequired() in apps/web-dashboard/src/lib/api.ts:65-70 collapses two distinct conditions into one boolean: "the orchestrator definitively reports setup is needed" versus "I could not reach the orchestrator / got a non-2xx." `if (!res.ok) return true;` returns setup-required for ANY network failure, 5xx, gateway 502 on cold boot, or timeout, making them indistinguishable from a genuine "no admin exists yet" signal. AuthGate.tsx:18-25 trusts that boolean (via useAuth's setupRequired) and hard-redirects every route to /setup. The real underlying cause is a fail-OPEN default on an unknown state: the code treats absence of a positive "setup complete" answer as proof setup is incomplete, violating this repo's "no guessing" standard (state must be read explicitly, never derived from a failure/absence). On a provisioned box the orchestrator is briefly unreachable on reboot, so it gets bounced into first-run setup where re-running AccountStep POSTs /api/auth/setup and surfaces a raw backend error.


**Options considered.**
- *A. Tri-state setup check + fail-closed retry gate in auth.tsx/AuthGate (chosen)* — **chosen**. Pros: Fixes the root cause directly: never routes to /setup on an unknown state. Boring, minimal blast radius - touches checkSetupRequired() (api.ts), the auth provider that exposes setupRequired (auth.tsx), and AuthGate. Matches the repo's fail-CLOSED-by-default posture and api.ts's own 503-as-data precedent (fetchSystemHealth). Adds a real retry UX so a 10-30s cold boot self-resolves instead of stranding the user. No new deps; reuses the existing DropletMark loading interstitial already in AuthGate. Cons: AuthGate/auth.tsx gain a small retry/backoff state machine and a transient connecting view; slightly more logic than a one-liner.
- *B. Invert the default: treat any non-OK as 'setup NOT required'* — **rejected**. Pros: One-line change in api.ts (return false on !res.ok); a provisioned box is never wrongly bounced to setup. Cons: Fails open the OTHER way - a genuinely fresh, unprovisioned box that hits a transient error on first boot skips the wizard and lands on a broken authed app with confusing errors. Still guessing from a failure signal, just the opposite guess. Does not satisfy 'no guessing'.
- *C. Server-side gate: orchestrator/gateway owns the setup-required redirect* — **rejected**. Pros: Centralizes the decision next to the source of truth; client cannot desync. Cons: Over-engineered for a launch blocker - new orchestrator middleware + gateway routing, larger blast radius. The orchestrator being unreachable is exactly the failure mode here, so a server gate cannot respond when it is down; the client must STILL handle 'orchestrator unreachable' gracefully, so this does not remove the need for option A.

**Recommended fix.** Make setup detection a tri-state that fails CLOSED. checkSetupRequired() must distinguish (a) confirmed setup-required, (b) confirmed setup-complete, and (c) indeterminate (network/5xx/timeout). Only a definitive, parsed positive answer (data.setupRequired === true on a 2xx) may route into /setup. Any indeterminate result must NOT redirect to the wizard: the auth provider (apps/web-dashboard/src/lib/auth.tsx) keeps setupRequired as a non-true 'unknown' marker and AuthGate renders a transient 'connecting to your appliance' retry interstitial with bounded backoff, retrying checkSetupRequired() until it gets a definitive answer. This mirrors the fail-CLOSED posture already in the repo (requireScope mount guards in apps/orchestrator/src/app.ts that deny by default; secret-absent surfaces fail closed rather than degrading open) and fetchSystemHealth's deliberate handling of 503 as data rather than a thrown error (api.ts:396-406). The redirect-to-setup path becomes the explicitly-confirmed branch, never the default fallthrough.

**Implementation steps.**
1. In apps/web-dashboard/src/lib/api.ts:65-70, change checkSetupRequired() from Promise<boolean> to a tri-state. Define `export type SetupStatus = 'required' | 'complete' | 'unknown'`. On a 2xx, parse JSON and return data.setupRequired === true ? 'required' : 'complete' (read the explicit field; do not infer from HTTP status). On non-OK (>=400), a thrown fetch error, or timeout, return 'unknown'. Wrap the fetch in try/catch and add an AbortController timeout (~5s) so a hung orchestrator yields 'unknown' rather than blocking. Mirror the defensive .json().catch pattern used throughout api.ts.
2. Read apps/web-dashboard/src/lib/auth.tsx to find where checkSetupRequired() is consumed and where setupRequired is exposed on the context (AuthGate reads it via useAuth). Update that provider to store the SetupStatus and expose setupRequired so that ONLY 'required' is truthy; add an exposed flag for the 'unknown'/connecting state (e.g. setupStatus: SetupStatus). On 'unknown', schedule a retry of checkSetupRequired() with bounded exponential backoff (e.g. 1s,2s,4s,8s capped ~10s) until it resolves to 'required' or 'complete'; never let 'unknown' present as setupRequired===true.
3. Update apps/web-dashboard/src/components/AuthGate.tsx:18-25 so the `if (setupRequired ...) router.replace('/setup')` branch only fires for confirmed 'required'. When status is 'unknown', render the transient connecting interstitial (reuse the existing DropletMark loading block at lines 47-58, copy like 'Connecting to your appliance...') and DO NOT navigate. Add a 'Retry now' affordance once backoff attempts are exhausted.
4. Grep apps/web-dashboard/src for every other caller of checkSetupRequired (and any reader of setupRequired) and migrate them to the tri-state so no caller keeps the old 'truthy means setup' assumption.
5. Confirm the orchestrator GET /api/auth/setup handler at apps/orchestrator/src/routes/auth.ts:224 returns an explicit { setupRequired: boolean } in its 2xx body (it already appears to). No orchestrator change needed unless it signals only via status code; the client must read the explicit field per the 'no guessing / explicit state' standard.
6. Add unit tests for checkSetupRequired() (vitest, alongside the existing apps/web-dashboard/src/__tests__ setup.* suite): 2xx setupRequired=true -> 'required'; 2xx setupRequired=false -> 'complete'; 500 -> 'unknown'; fetch throw -> 'unknown'; AbortController timeout -> 'unknown'.
7. Add an AuthGate component test (React Testing Library, matching existing setup.flow.test.tsx / setup.e2e.test.tsx patterns) asserting 'unknown' does NOT navigate to /setup and renders the connecting interstitial, a subsequent 'complete' resolves to the app, and 'required' DOES navigate to /setup.
8. Run `npm test` in apps/web-dashboard (vitest) and lint; manually verify by loading the dashboard against a stopped orchestrator (expect connecting interstitial, no /setup redirect) then starting it (expect auto-recovery).

**Acceptance criteria.**
- checkSetupRequired() in api.ts returns a tri-state ('required'|'complete'|'unknown'), never a bare boolean, and returns 'unknown' for every non-2xx response, fetch/network error, and timeout.
- A non-2xx or unreachable /api/auth/setup NEVER causes a redirect to /setup; AuthGate renders the connecting/retry interstitial instead.
- Only an explicit parsed positive answer (data.setupRequired === true on a 2xx) routes a user into the /setup wizard.
- On a provisioned box that boots while the orchestrator is briefly down, the dashboard shows a connecting state and auto-recovers to the normal app once the orchestrator answers - never stranded in setup.
- A genuinely fresh, unprovisioned box still reaches /setup once the orchestrator confirms setupRequired:true.
- Unit tests (required/complete/unknown) and an AuthGate component test (unknown does not redirect; required does) exist and pass in CI via vitest.

**Test strategy.** Use the web-dashboard's existing vitest + React Testing Library harness (apps/web-dashboard/vitest.config.ts; sibling tests in src/__tests__/setup.flow.test.tsx, setup.e2e.test.tsx). Add api-level unit tests mocking authFetch/global fetch to lock the tri-state mapping: 200+setupRequired:true, 200+setupRequired:false, 500, network throw, and an aborted/timed-out request all map to the correct SetupStatus. Add an AuthGate component test that mocks the auth context to status 'unknown' and asserts no router.replace('/setup') occurs and the connecting interstitial renders, then re-renders with 'complete' and asserts the app shell renders; plus a case where 'required' DOES call router.replace('/setup'). These tests fail CI if anyone re-introduces 'non-OK => setup required', preventing regression.

**Risks.**
- The 'unknown' retry path depends on backoff parameters covering realistic cold-boot windows (orchestrator + Prisma migrations can take longer than a few seconds). Too-short backoff that gives up and shows a hard error would reintroduce a poor first-boot UX - pick a generous cap plus a manual 'Retry now' fallback.
- auth.tsx currently exposes setupRequired as a boolean consumed by AuthGate; the migration to tri-state must update both the provider and AuthGate together (and any other readers found via grep) to avoid a half-converted boolean assumption lingering.
- If a genuinely fresh box's orchestrator is up but /api/auth/setup returns 5xx due to a real backend bug, the new behavior shows the connecting interstitial instead of the wizard (correct - it should not enter half-broken setup), but the underlying error must be surfaced/logged so an operator can diagnose rather than seeing an endless spinner.
- Confirm GET /api/auth/setup (apps/orchestrator/src/routes/auth.ts:224) always includes an explicit setupRequired field in its 2xx body; if any 2xx path omits it, the client would read undefined and must treat that as 'unknown', not 'complete'.

**Files.** `apps/web-dashboard/src/lib/api.ts`, `apps/web-dashboard/src/lib/auth.tsx`, `apps/web-dashboard/src/components/AuthGate.tsx`, `apps/web-dashboard/src/__tests__/setup-detection.test.tsx`

## WARP-221 — Migrate camera-discovery top-level discovery_loop from while True to AsyncIOScheduler (enrich WARP-221)

**Area:** release · **Severity:** high · **Effort:** S


**Root cause.** camera-discovery's periodic scan driver, discovery_loop() at services/camera-discovery/main.py:559-575, schedules its recurring sweep with the banned `while True: ... await asyncio.sleep(SCAN_INTERVAL)` pattern (main.py:570) that CLAUDE.md's scheduling standard prohibits. The service never adopted the canonical apscheduler scheduler — it is absent from services/camera-discovery/requirements.txt, while services/routing/scheduler.py already demonstrates the AsyncIOScheduler pattern. The loop is launched via asyncio.create_task(discovery_loop()) in the @app.on_event("startup") handler (main.py:631). WARP-221 already lists camera-discovery's inner ONVIF scan and the switch keepalive, but its scope never captured this outermost top-level scheduling loop — the most visible violation on a launch service is untracked.


**Options considered.**
- *AsyncIOScheduler interval job in FastAPI startup/shutdown (copy services/routing/scheduler.py)* — **chosen**. Pros: Matches the documented canonical pattern used by routing + 4 other services; removes the CLAUDE.md violation cleanly; AsyncIOScheduler runs on the existing event loop so no thread-safety concerns for the async scan/ONVIF calls; max_instances=1 + coalesce add overlap protection the while-True loop never had; reviewers already recognize this shape. Cons: Adds apscheduler to one more service's requirements (already an accepted, pinned dependency repo-wide); requires extracting the loop body into a standalone coroutine and moving the Frigate-readiness wait.
- *Keep the loop but swap while True for an asyncio.Event-gated wait* — **rejected**. Pros: Smaller diff; no new dependency. Cons: Still a hand-rolled scheduler, which is exactly what the standard forbids — it would not satisfy CLAUDE.md or close the WARP-221 item; no coalesce/max_instances safety; diverges from the four services already standardized on apscheduler. A band-aid that masks the issue.
- *BackgroundScheduler (thread-based) instead of AsyncIOScheduler* — **rejected**. Pros: Also an apscheduler API; CLAUDE.md lists it as acceptable for non-asyncio services. Cons: camera-discovery is an asyncio FastAPI service doing async scan/ONVIF/httpx I/O; a thread-based scheduler forces cross-thread coroutine scheduling and contradicts the 'AsyncIOScheduler for asyncio services' guidance. Wrong tool for an async service.

**Recommended fix.** Enrich WARP-221 to add this top-level discovery_loop as an explicit in-scope item, then replace the while-True driver with an AsyncIOScheduler interval job wired into the FastAPI startup/shutdown handlers, copying the canonical pattern from services/routing/scheduler.py (start_throughput_scheduler). Extract the loop body into an idempotent `async def run_scan()` (preserving the existing try/except so a failed sweep never kills the schedule), keep the Frigate-readiness wait as a one-time startup step, and register `scheduler.add_job(run_scan, "interval", seconds=SCAN_INTERVAL, id="camera-discovery-scan", max_instances=1, coalesce=True, next_run_time=datetime.now())` so the first sweep still fires immediately. Start the scheduler in @app.on_event("startup") and `scheduler.shutdown(wait=False)` in the existing @app.on_event("shutdown") (main.py:634), mirroring routing's main.py start/stop (main.py:211-241). Pin `apscheduler` in services/camera-discovery/requirements.txt at the same version routing uses. This is the boring, proven, minimal-blast-radius fix: it matches the four sibling services, removes the standards violation, and adds overlap protection (max_instances=1/coalesce) the bare while-True loop lacked.

**Implementation steps.**
1. Enrich the WARP-221 Jira ticket: add a checklist item 'camera-discovery top-level discovery_loop (services/camera-discovery/main.py:570) — replace while-True scan scheduler with AsyncIOScheduler' and note in the description that the original scope (inner ONVIF scan + switch keepalive) missed this outermost loop.
